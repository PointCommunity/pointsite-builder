Architecture and limits

Keep React/Puck and the existing Hono application. Add a Node runtime entry point, static-file delivery, graceful shutdown and a bounded non-overlapping scheduler. Use Node SQLite on a Ceph RWO volume with one writer, WAL, foreign keys, a busy timeout and transactional migration checksums. Use the same schema in both fresh environments. Media remain in the existing private SQL storage model; do not add object storage merely for this move.

Backups must use SQLite's consistent backup API, integrity checks and atomic publication of completed backup files. Keep workspace and deletion/recovery authority separately identifiable; restoring a workspace must not restore older deletion authority, revive expired checkouts or replay completed publication work. Store private backups outside the application data volume through the existing homelab backup facility, with a concrete retention schedule and a disposable restore rehearsal before release. A backup failure must be visible; never copy an active SQLite main file without its consistency protocol.

Native restore keeps the live control database, replays committed deletion receipts into a disposable backup copy, clears checkouts and preflights, and compares protected roles, publication state and schema with the current workspace before replacement. A mismatch keeps access quarantined and refuses the restore; it never revives older authority or publication jobs. Restore accepts backups at most 35 days old, inside the 90-day deletion-receipt window. Recovery increments the session epoch, invalidating pre-recovery sessions and OAuth state. Future image rollback requires demonstrated schema compatibility with the preceding digest; unknown migrations are not silently accepted.

Use current Production as a verified draft source, not as a writable database. Capture the exact source commit before collecting content and media; reject a source change that invalidates the import. Import must preserve routes, text, forms, links, theme intent and image bytes. Every created draft owns its independent media and history. Existing old drafts are neither imported nor deleted. The initial trusted Administrator must be established through the existing verified GitHub identity and role model, never a first-visitor privilege grant.

Source capture follows the currently deployed Pages artifact, including content rollback. New publication attestations record sourceCommit; rollback records the original content commit rather than the current branch or runner commit. Capture checks the current native Pages deployment before and after reading immutable input/output manifests and hash-verified public images. Only the recorded original-site baseline may use the reviewed legacy conversion. Unknown formats and changing deployments fail without creating a draft. A lost-response retry returns its original draft before contacting Production again.

Reconcile unfinished public rollback work before host changes are considered releasable. Remove homelab dependence on D1 quota analytics, Worker deployment APIs and Time Travel. Retain useful autosave, checkout, SQL efficiency, deletion protection and publication integrity. Provider-specific code retained for the old Worker path must not execute or require credentials in the homelab path. Admin status must show actual local storage/readiness and backup freshness, not fabricated D1 usage.

Canary and Production may target the same public Staging repository only through explicit publication, immutable input capture, Git compare-and-swap, native workflow concurrency and deployment-identity checks. A candidate from one Builder must invalidate stale acceptance in the other. Production runner authentication must trust only the Production Builder origin. Canary cannot obtain a Production publication capability through UI or direct API. Workflow inputs accept only the two explicit native Builder origins; Production callbacks use its fixed origin. Signed OIDC audiences include that origin, job and nonce. A shared pointsite-pages-TARGET concurrency group spans each complete publication, verification and rollback run without cancelling the active run. Queued stale work still must pass expected-base and native deployment checks. See the GitHub concurrency contract.

Native HTTP uses the official @hono/node-server adapter, pinned to 2.1.1 (registry metadata checked September 14). Hono documents this adapter for Node request/response conversion and static serving. Reuse it instead of hand-writing stream and cookie handling; application origin, body-limit and private-path guards remain explicit.
