September 14, 2026. Tasks H11–H13. Commands run inside the selected Builder pod with its mounted environment and volumes. They have no HTTP endpoint. Confirm the namespace, hostname and running image before operating. This document describes the implementation; live storage and Canary qualification remain pending.

Normal operation

One application replica owns SQLite workspace and independent recovery-control files. Both use WAL, full synchronization and foreign keys. The image contains schema migrations and a checksum ledger; changed, unknown or untracked schema prevents startup. Persistent files remain outside the container filesystem.

Startup requires an off-volume backup directory and makes the first backup before readiness. Subsequent backups run every 24 hours through the application scheduler. SQLite's online backup API creates a self-contained workspace copy, then a newer control copy. A manifest records environment, instance, timestamps, file sizes and SHA-256 checksums; incomplete directories are never restore candidates.

Keep the newest successful copy on each of seven days and four weeks. A pinned marker preserves selected recovery evidence. Monitor Admin for failures or a last-success timestamp older than 24 hours. A failed copy does not delete a preceding successful backup. Backup snapshots include private draft content; keep storage private.

Read status or force a backup

node dist/server/operator.js status returns the environment and instance ID, recovery epoch/mode, latest successful backup ID and timestamps. Status does not create a backup. node dist/server/operator.js backup makes a new verified pair on the mounted off-volume destination. A database path typo must fail; the operator does not initialize replacement databases.

Restore a selected workspace

  1. Obtain task-specific authorization for the data restore. Record the current image digest, source/tree, GitOps revision, status output and selected backup manifest. This hosting implementation authorizes only disposable restore rehearsals.
  2. Inspect a completed backup no older than 35 days. Confirm its origin and instance match the live control database. Deletion receipts are retained for 90 days, beyond this restore window. A pinned older backup is evidence, not permission to bypass the window.
  3. Generate a recovery UUID and record the current active epoch from status. Run node dist/server/operator.js quarantine CURRENT_EPOCH RECOVERY_ID. Quarantine increments the epoch and prevents new workspace requests and scheduled jobs. Readiness becomes unavailable; liveness stays healthy. Do not delete or replace the live control file.
  4. Let existing invocation leases drain. The restore command checks SQLite's clock against the recorded deadline; an early attempt returns WORKSPACE_RECOVERY_DRAINING. Use status to inspect the deadline. No guessed sleep or process timing substitutes for this check.
  5. Run node dist/server/operator.js restore BACKUP_ID QUARANTINED_EPOCH RECOVERY_ID. The exact selection is recorded immutably and pinned. The operator verifies hashes and origin, replays later committed deletions into a temporary workspace, and compares protected roles, publication state and schema with current authority. A mismatch leaves the application quarantined and the live workspace unchanged.
  6. After validation, SQLite replaces the workspace through its transaction and WAL machinery. Checkout/preflight state is cleared, integrity is checked, and the live control epoch advances before requests resume. Existing sessions and unfinished OAuth requests become invalid. Sign in again and verify deliberately deleted drafts remain absent, surviving draft content matches the selected backup, and completed publications have not replayed.
  7. Take a fresh backup and record its manifest, health/readiness and authenticated behavior. Retain the selected pinned recovery evidence until separately approved cleanup.

Never restore a control snapshot over live authority, copy a live SQLite main file without its WAL, or silently reset an unreadable database. A failed protected-state comparison requires operator investigation; there is no force flag. Losing both live control authority and its independent storage is outside this automated workspace restore procedure.

Retain the preceding Production image and GitOps configuration. Roll back by digest without rebuilding only when that image understands the current schema. Unknown/changed migrations fail closed; image rollback does not restore data automatically. Rehearse compatibility against disposable copies before publishing a schema-changing candidate. First homelab deployment retains the old Worker/D1 environment as fallback; its state is not a synchronized copy of new homelab drafts.
