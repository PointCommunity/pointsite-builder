Operator handbook

Production instructions are documentation, not authorization. Stop on any failed gate. Never repair staging by writing directly to production.

Independent drafts and Library lifecycle

Each draft owns its complete document, Library, private images, linked-media records, and revision history. Creating or duplicating a draft creates independent contents. Changes to one draft cannot change another draft. Content drafts are database workspaces; application Git branches are separate from those workspaces.

Archive sets aside the entire draft and freezes its contents. Unarchive restores that workspace for editing. Delete is available only after archive and requires the exact typed confirmation DELETE. Confirmation permanently purges all private contents and history together. There is no 30-day recovery window. Only content-free deletion and audit evidence remains; purged content must never return through retries or restoration.

Publishing creates an independent destination copy of the selected document and every required local image. Deleting the source draft does not affect completed Staging or Production copies. External HTTPS images, videos, and YouTube resources remain external; their records are copied with the document. An active publication operation must finish or be safely cancelled before source-draft purge.

Manage Library items

  1. Open an active draft with an owned checkout. Wait until all changes are saved.
  2. Open Library to see managed images, uploaded images, and linked media in one inventory. Upload creates one item immediately.
  3. Search names, file or source details, descriptions, tags, and media types. Sort by date added, date updated, name, or usage in this draft. Reset clears the keyword and restores newest-added sorting.
  4. Archive an item to set it aside in Archived items. Its current placements and retained revisions still work. Unarchive preserves the item and its metadata.
  5. Permanent item deletion requires archive first and a final Yes confirmation. Current placements, retained revisions, or pending publication references block deletion with an explanation. Use Unarchive to recover an item that is still needed.
  6. Replace image is available for images only. Select a valid file, inspect the local preview, write fresh alternative text, and review the final irreversible confirmation. Cancel discards the proposed change. Successful replacement updates current placements in this draft while preserving other drafts, retained snapshots, and published copies.

Viewer access is read only. Whole-draft purge intentionally removes all private history; individual item deletion preserves history still owned by a surviving draft. Completed publication copies alone never require retaining private source images.

The Issue 32 isolation specification supersedes the historical soft-delete and 30-day draft recovery policies in specifications 001 and 003. The asset ownership migration runbook governs migration checks, legacy orphan recovery, and compatible application rollback.

Failed staging publish

Prerequisites
Request ID, job ID, revision/checksum, candidate checksum, and displayed staging base SHA.
Safe command
gh run list --repo PointCommunity/pointsite-staging --branch codex/builder-renderer --limit 10
Expected result
The exact candidate run identifies a deterministic failure or completes both verify and deploy. An occupied shared slot reports only its queued/running phase and bounded recovery time; it never identifies another private draft or operator. Candidate upload happens in batches of at most 20 blobs per request, with durable checkpoints. Builder continues the same job automatically while it runs. Upload progress is not publication success: all required images and documents must be present before the Staging branch changes, then normal verification must pass.
Stop condition
Base drift, a path outside the candidate file allowlist, incomplete live evidence, or an unknown commit.
Recovery
Use Builder's Check availability action first. A queued or running job has a 15-minute lease; an expired lease is safely cancelled and audited before the exact draft retries. After an interruption, reopen the same draft's publishing panel. Builder resumes the existing job through guarded continuation requests and reuses completed blob uploads; status reads never advance publishing. Do not start a competing publication to recover a running job. If the draft, renderer, or Staging base changed, refresh the candidate and pass preflight again. Never bypass a revision or lease conflict.

Compact storage activation

Use this sequence only for a fully validated release. Keep other deployments and rollbacks paused during conversion.

  1. Apply additive schema migrations through 0019 and complete draft-media ownership migration. Deploy a compatible reader with legacy writes first.
  2. Verify the exact release source SHA from a clean checkout. Dirty builds fail the reader gate. This command reads Cloudflare deployment state and uncached health; it performs no database writes. 
    npx tsx scripts/compact-storage.ts --verify-reader <source-sha>
  3. Enable DRAFT_STORAGE_FORMAT=compact-v1 in the controlled release, deploy, then verify its exact source SHA again. Mixed traffic or a missing/mismatched native Worker version ID fails verification. The deployed version must bind DB to the intended PointSite Builder database.
  4. Inspect remaining conversion counts without changing storage. 
    npx tsx scripts/compact-storage.ts --status
  5. Run conversion using that verified source SHA. The CLI uses Wrangler authentication and rechecks deployment around each batch of at most eight atomic steps. 
    npx tsx scripts/compact-storage.ts --apply <source-sha>

On interruption or a changed deployment, inspect the current release before resuming. Completed steps remain recorded and are skipped on restart. A corruption error requires diagnosis; do not delete the source or force conversion. Status and logs contain counts and release metadata, never draft bodies or credentials. After any compact payload exists, rollback only to a verified reader supporting both storage formats. A pre-bridge binary or removal of the compact schema is not a compatible rollback.

Database recovery

Prerequisites
An approved infrastructure incident, an exact selected Time Travel bookmark, a maintenance window with no other database operator or deployment, the clean deployed Builder source, and a scoped Cloudflare credential retrieved through the native 1Password CLI. This is infrastructure recovery; routine publication retry and verification remain inside Builder. Both workspace and independent recovery migrations must already be deployed, and media ownership migration must be complete. Resolve all active or uncertain publication executions before preparing a database restore.
Safe command
npx tsx scripts/workspace-recovery.ts --action status --credential-ref op://VAULT/ITEM/credential
Expected result
Native account/database identities and the deployed source match. Status reports the independent epoch, quarantine state and recovery phase without draft contents or secrets. The helper uses the native Cloudflare D1 HTTP API with atomic statement batches; it never starts a local server or saves a local database, credential or private backup.
Stop condition
Wrong source/account/database, unreadable independent receipts, unresolved publication, undrained access, pending deletion settlement, incompatible schema/authority/publication history, referenced deleted content, integrity failure, or an uncertain native restore response. Keep workspace access closed. Never bypass a failed check by editing a role, receipt, recovery phase or stored hash.
Recovery
Cloudflare Free provides seven days of in-place Time Travel. It is not an independent backup and does not clone a database. Rehearse the protocol using synthetic fixtures. Never rewind the separate recovery database together with the workspace.
  1. Record status, a new incident UUID and the current epoch. Run the helper with --action quarantine --epoch CURRENT --id INCIDENT, retaining the credential reference on each command. Use the returned quarantine epoch for subsequent actions.
  2. Run --action settle --epoch QUARANTINE --id INCIDENT. The native clock must show all old invocation leases expired. Each successful call settles at most 20 uncertain deletions from atomic commit proofs. Repeat until it reports zero. An unreadable workspace cannot safely resolve unknown deletion outcomes and must remain closed.
  3. Run --action prepare --epoch QUARANTINE --id INCIDENT --bookmark TARGET. This records hashes of the schema, roles, approvals and publication records plus the native pre-restore bookmark. Retain that bookmark with the incident record.
  4. After incident-specific approval of the destructive target, run --action restore --epoch QUARANTINE --id INCIDENT --allow-restore once. A lost or ambiguous response stays in the restoring phase and cannot automatically retry. Native provider reconciliation is required before any further destructive operation.
  5. Run --action replay --epoch QUARANTINE --id INCIDENT until it reports zero. Each call reapplies one committed deletion atomically and advances a durable cursor. Interrupted calls can resume. Historical references to deleted Library content block the incompatible bookmark instead of returning the deleted content to users.
  6. Run --action reopen --epoch QUARANTINE --id INCIDENT. Reopening requires identical protected state, complete deletion replay, integrity checks and removal of old checkout tokens. Read status again, verify readiness with real authorized access, and require editors to acquire fresh checkouts. An incompatible bookmark needs a separately reviewed native recovery to a compatible later bookmark or the recorded pre-restore point; this helper deliberately provides no force-open action.

Provider retention expires; no unlimited recovery guarantee exists. Deliberate deletion prevents Builder access and is reapplied before any supported restore reopens. Provider Time Travel may retain old bytes until its own retention expires. Never place private database exports in public GitHub repositories, Actions artifacts or unencrypted local files.

Credential rotation

Prerequisites
Administrator access, credential inventory, narrow replacement scope, and rollback owner.
Safe command
npx wrangler secret put GITHUB_APP_PRIVATE_KEY
Expected result
Identity succeeds and one read-only staging-base request returns the expected repository SHA.
Stop condition
Unexpected App installation, production repository access, secret in output/source, or failed identity check.
Recovery
Restore the prior secret if still valid; otherwise disable publishing, revoke both credentials, issue a new narrow credential, and audit the event.

Quota response

Prerequisites
Administrator capacity view, provider usage readback, audit sample, and retention dry-run export.
Safe command
Export a current BUILDER_SESSION_COOKIE, then run npm run maintenance -- --url "$BUILDER_URL".
Expected result
Dry-run only: candidate counts and an export checksum are returned; no object is deleted.
Stop condition
Usage disagrees with provider readback, ownership is unknown, current/named/referenced data appears in candidates, or export is unavailable. The legacy global-media cleanup path is retired; never use global asset deletion to reclaim storage owned by surviving drafts.
Recovery
Pause uploads/publishes, find the growth source, then apply the unchanged exported plan through the administrator endpoint.

Staging rollback

Prerequisites
Last accepted staging commit, failed exact commit, passing evidence for the known-good commit, and reviewed rollback branch.
Safe command
gh pr create --repo PointCommunity/pointsite-staging --base main --head codex/staging-rollback --title "Rollback staging candidate"
Expected result
The reviewed revert deploys; all protected live routes, headers, checksums, accessibility, and primary flow pass.
Stop condition
Unknown known-good SHA, unrelated diff, failed check, missing GitHub authentication, or production remote in the write target.
Recovery
Leave the last passing deployment active, correct the rollback branch, and rerun exact verification. Never force-push main.

Production rollback

Prerequisites
Production enablement completed after G5, explicit authorization for the exact release, prior known-good production SHA, incident owner, and reviewed revert PR.
Safe command
gh pr create --repo PointCommunity/pointsite --base main --head codex/production-rollback --title "Rollback approved PointSite release"
Expected result
Only the reviewed revert is merged; Pages deploys that exact SHA and cache-busted live probes match the known-good candidate.
Stop condition
No explicit authorization, candidate/base mismatch, unrelated diff, failing required check, or unverifiable known-good SHA.
Recovery
Keep the incident open, do not bypass branch protection, prepare a corrected reviewed revert, and retain all release/audit evidence.
