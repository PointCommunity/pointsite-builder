ADR 0001: PointSite Builder architecture and release boundary

Status: Accepted
Date: 2026-09-05
Owners: PointCommunity administrators

Decision 1: Isolate production with independent repositories

Context

The existing public site must remain unchanged while nontechnical authoring, renderer, and release behavior are proven. A same-owner GitHub fork is not a reliable organizational topology, and direct production branches would expose unfinished work to the production repository.

Decision

PointCommunity/pointsite-builder contains the private authoring application. The independent private PointCommunity/pointsite-staging repository contains the candidate public renderer. PointCommunity/pointsite remains production and receives no implementation until the staging acceptance gate passes.

Alternatives considered

  • Build inside production: rejected because it weakens isolation.
  • Use a same-owner fork: rejected because GitHub does not support the desired topology consistently.
  • Use only feature branches: rejected because repository-level deployments and permissions would still be shared.

Consequences

Renderer snapshots and documents cross a controlled repository boundary. This adds synchronization checks, but production remains auditable and untouched throughout development.

Decision 2: Use Puck behind a controlled component registry

Context

Administrators need visual layout editing without arbitrary code, while PointSite needs predictable semantics, accessibility, security, and static output.

Decision

Use Puck as the lazy-loaded editor canvas. Puck may only author strict, versioned PointSite blocks and bounded variants. The same project-owned renderer consumes the validated document for preview and public output.

Alternatives considered

  • Build drag-and-drop infrastructure from scratch: rejected for cost and accessibility risk.
  • Embed an unrestricted page builder: rejected because arbitrary markup and scripts violate the trust boundary.
  • Use a text-only CMS: rejected because it does not meet visual editing needs.

Consequences

Admins gain visual editing and keyboard/button alternatives. New public capabilities require an explicit schema, renderer, tests, and migration rather than ad hoc HTML.

Decision 3: Store drafts and chunked private media in D1

Context

Drafts need revisions, optimistic concurrency, auditability, recovery, and low operational cost. Media must stay private before publication and cannot safely live in public Git history while being edited.

Decision

Use Cloudflare D1 for roles, drafts, immutable revisions, jobs, approvals, audit records, media metadata, and one-megabyte private media chunks. Enforce a 250 MB media cap below the 500 MB Free database limit. Publish only referenced, approved assets to staging Git.

Alternatives considered

  • Store drafts directly in Git: rejected because autosave would create noisy history and complex conflicts.
  • Store media publicly: rejected because unpublished material would leak.
  • Add a separate hosted database vendor: rejected because it adds cost and another operational surface without a first-release need.

Consequences

Atomic D1 transactions protect revision pointers and chunk writes. Free-tier exhaustion fails closed instead of billing; lifecycle and capacity controls remain mandatory.

Decision 4: Authenticate with the staging-only GitHub App

Context

The builder is private and role-sensitive. An edge login alone does not remove the need for application-level identity and authorization.

Decision

Use GitHub App OAuth with state and PKCE. The Worker validates a signed, Secure, HttpOnly session, stable GitHub user ID, current staging-repository collaboration, and active local role on every request. Development bypass is local-only and fails closed elsewhere.

Alternatives considered

  • Cloudflare Zero Trust Access: rejected because even its Free onboarding requires payment details, violating the no-payment boundary.
  • Build application passwords: rejected because it duplicates identity and account-security work.
  • Authorize all logged-in users equally: rejected because publishing and role administration need separation of duties.

Consequences

Collaboration or role removal takes effect on the next request. OAuth, App, and session secrets stay in Worker secrets; authorization decisions are audited without logging tokens.

Decision 5: Distribute a versioned renderer snapshot

Context

Preview and published output must not drift, but the public site must remain static and must not import private builder services.

Decision

Package the site schema, renderer, styles, migration registry, and version identity as a deterministic site-kit snapshot. Staging vendors the exact snapshot with checksums. Preview and static export both render the same validated SiteDocument.

Alternatives considered

  • Fetch drafts from the public site at runtime: rejected because it creates a public dynamic dependency.
  • Maintain separate preview and public renderers: rejected because their behavior would drift.
  • Publish an unpinned floating package: rejected because a candidate could change without a matching content revision.

Consequences

Every candidate records document checksum, schema version, renderer version, and Git SHA. Sync tooling must reject unexpected differences.

Decision 6: Make production a separately approved exact-candidate gate

Context

A convenient publish button must not convert a drafting mistake or compromised builder session into an immediate public-site change.

Decision

Publishing first creates an idempotent staging job and exact candidate evidence. Production integration is absent until staging acceptance. Later, a Publisher may prepare a production pull request for that exact candidate, but merge and production publication require separate recorded approval and passing protected checks. No browser action pushes directly to production.

Alternatives considered

  • One-click direct production deploy: rejected because it lacks review and rollback evidence.
  • Automatically merge after staging: rejected because staging success is readiness evidence, not production authorization.
  • Copy files manually: rejected because it is error-prone and difficult to audit.

Consequences

Publishing remains simple for admins but deliberately has visible stages: save, preview, publish to staging, verify, prepare production, approve exact candidate, merge, and verify production.
