Data ownership and mutation contracts

Specification · Proposed implementation contract

Ownership model

Record Ownership and lifetime
Draft and revisions The draft owns full document snapshots, labels, editor/checkouts, and private preflight state. Archive preserves them together; purge removes them together.
Library item Compound owner/item identity, image/video/YouTube type, managed/uploaded/linked origin, display and accessibility metadata, creation/update timestamps, archive timestamp, and current binary binding where applicable.
Binary version Draft owner, immutable version identity, source-path binding, private object key, checksum, MIME, dimensions, byte size, and chunks. Replacement creates a new version; duplication copies into another owner. Retained revisions keep their existing bindings.
Operation receipt Draft/operation identity and request hash, with no retained draft payload after purge. Deleted operation keys cannot replay a stale document. Purge retries report completion safely.
Published snapshot Destination-owned document, manifest, renderer-compatible file paths, and binary files. Minimal immutable publication receipts remain independent of private draft storage.
Deletion audit Content-free actor/action/time/request and opaque deleted identity. No document, image, name, alt text, link, or private object key survives in the tombstone.

API contract

  • Library listing is scoped to /api/drafts/:draftId/library and returns the complete item set, active/archived counts, item usage and safe blockers, plus the draft's current revision identity.
  • Every Library mutation includes the owning draft, current checkout, exact revision precondition, and idempotency key. Authorization, same-origin headers, rate limits, body bounds, and schema validation remain server-enforced.
  • Upload and replacement accept multipart image bytes and fresh accessibility metadata. Upload becomes visible in the unified Library immediately. Replacement submission carries the final confirmation; no storage mutation occurs during local preview.
  • Archive, unarchive, metadata update, and individual deletion address one item under its draft. Deletion independently validates archive state, final confirmation, references, and retention at commit time.
  • A successful mutation returns the committed draft/revision and canonical Library state. The client adopts it only after pending autosave is settled; it never overwrites newer local changes with a stale response.
  • Private image reads resolve a draft-owned immutable version. A cross-owner reference or purged version returns Not Found. Published documents use destination-relative asset paths and need no Builder session.
  • Whole-draft DELETE retains archive-first and typed DELETE confirmation, returns only a content-free deletion receipt, and performs no GitHub or public-site mutation.
  • OpenAPI must document owner paths, payloads, safe response DTOs, conflict/precondition responses, confirmation rules, pagination/completeness, and deletion semantics before endpoint implementation.

Transactions and invariants

Changes to a document, Library state, private chunks, version bindings, idempotency receipt, and audit are committed together. Guard owner, archive state, checkout, current revision, capacity, and publication lease within the transaction. Do not perform a storage delete before committing its metadata transaction. Never overwrite a referenced binary in place.

All retained versions of a surviving draft remain protected. Individual media deletion cannot bypass those references. Whole-draft purge removes the entire ownership graph; completed publications are separate owners and remain valid. Any failed guard leaves all bytes and metadata unchanged.

Migration and rollback

  1. Inventory all drafts, retained revisions, assets, chunks, pending jobs, idempotency payloads, and foreign-key dependencies. Record aggregate counts and checksums without exposing draft contents.
  2. Add ownership/version metadata without dropping existing content. Bind every historical reference to an owned immutable copy. For assets shared by legacy drafts, create separate copies for each owner. Preserve revision JSON and checksums.
  3. Preserve legacy uploads with no provable draft owner in an explicit archived recovery workspace. Do not silently assign them to every active draft or discard them. Verify copy checksums and capacity before migration commits.
  4. Rehearse on synthetic populated databases, including interrupted migration and rerun. Verify ownership, timestamp derivation, unchanged historical checksums, no cross-draft mutation, and exact binary equality.
  5. Retire legacy global writes and unsafe orphan cleanup only after the owned data and new read paths are complete. Remove redundant legacy private bytes only after verifying every necessary owned copy. No automatic purge of previously soft-deleted user data is part of deployment.
  6. Verify the recorded application rollback version against the migrated schema and paths. If it would restore shared mutable behavior or cannot read new versions, establish and verify a compatible recovery build before enabling lifecycle mutations. Never treat rolling back to an incompatible worker as recovery.
  7. Application rollback must not restore purged draft content. A confirmed purge is irreversible. Preserve independent published copies and content-free audit evidence during recovery.
