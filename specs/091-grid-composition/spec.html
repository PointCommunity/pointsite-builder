Issue #91 · Grid-composable site elements

Specification for the approved GitHub Issue. The Issue's twelve acceptance criteria and boundaries are authoritative; this document adds the technical contract and verification map without changing its scope.

Assumptions for review. Legacy Point content stays intact and visually equivalent. New Point-branded layout options disappear from authoring, but legacy variants remain readable during transition. A composed layout is authored through Builder controls, never arbitrary HTML/CSS/JavaScript. Public-site publication remains an authenticated Administrator action, not part of this task.

Objective and inventory

Any visible page or global region can be rebuilt from brand-neutral, independently placed text, image, button/link, form, media, navigation, and grouping primitives on responsive snapping grids. The inventory includes all registered elements (Hero, Heading, Rich Text, Image, Linked Media, Split Feature, CTA, Cards, People, FAQ, Form, Map, Divider, Spacer, Text, Button, Navigation, Social Links), page sections, editable header and footer, reusable collections, and Form Designer fields. Existing specialized renderers are compatibility inputs, not the only way to obtain those appearances.

Concern Required contract Baseline evidence

Compatibility and recovery

Existing v9–v11 drafts and revisions must load and retain their current appearance. Migration is deterministic and idempotent. New composition data cannot be saved until the retained rollback image can read it; introduce a compatibility-capable baseline before authoring activates, or demonstrate an equivalent rollback-safe sequence. Test upgrade and previous-image reads against representative serialized drafts before Canary. Do not bulk-rewrite Production drafts, erase old variants, or restore data as an application rollback.

Success criteria and testing

Use Issue #91 acceptance criteria 1–12 without weakening them. Record an inventory fixture for every legacy block/variant and representative site pages. Test document migration and readback, child coordinates and collision/layers, semantic/empty rendering, image link safety, crop/focal/fit, per-image controls, form field flow, phantom-to-drop geometry, direct-page insertion, autosave/revisions/undo, and Layout–Preview–generated parity. Browser-check desktop, tablet, mobile, 200% zoom, pointer/keyboard/touch, accessibility, and the actual pictured layouts in an isolated draft. Run repository checks sequentially.

Commands and structure

Source: src/site-kit/ shared schema/renderer, src/client/editor/ Puck authoring, src/client/settings/FormsEditor.tsx, src/server/publish/; tests in tests/unit/, tests/integration/, tests/e2e/. Follow strict TypeScript, existing discriminated schemas and CSS tokens; e.g. const next = updateGridArea(item.grid, breakpoint, { row: 2 });. Use npm run check, then npm run test:performance, then npm run test:e2e -- --workers=2, plus focused npx vitest run <test file> --maxWorkers=4, npm run pipeline:health and git diff --check. The repository's fresh-worktree QA prepare/cleanup and exact-candidate release gates also apply.

Boundaries

Always preserve unrelated work, legacy content, accessible semantics, safe URL/media validation, authorized checkout/revisions, and correct publication lanes. Ask for PM approval of any Issue-body change, destructive data action, or exact Canary candidate before merge and Production promotion. Production completion needs no second PM approval. Never use arbitrary script/style injection, expose private media or credentials, publish public site content from chat, or claim a passing test that was not run.
