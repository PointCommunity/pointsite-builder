Objective and acceptance

Editors maintain named Navigation designs within a draft and assign each Navigation element a stable design reference. A design edit updates every consumer across pages, previews and the published candidate. Layout position, responsive grid size, accessible label, alignment, orientation and surface remain independent element properties.

  • Create, select, rename and safely delete designs; show consuming pages and elements.
  • Support ordered top-level links and exactly one level of ordered child links.
  • Provide drag reordering plus ordinary buttons/selects for pointer and keyboard alternatives.
  • Use the existing validated destination control, action autosave and immutable revision history.
  • Migrate existing navigation deterministically without changing links, styling or placement.
  • Reject missing references, duplicate identities, invalid destinations and deeper nesting.
  • Keep new Navigation elements immediately movable and resizable at every grid breakpoint.
  • Audit every specified Builder surface and remediate evidenced shared control-density problems.
  • Use Navigation Designer, Layout Designer and Form Designer terminology; retain compact tab names.

Proposed document model

Version the changed contract explicitly. A Navigation design contains a UUID, trimmed display name, and ordered items using the existing link shape and limits: 20 top-level links, 12 children per parent, 60-character labels. Propose at most 30 designs, matching the existing form count limit, with 120-character names and at least one design. Validate duplicate design IDs and duplicate item IDs within a design. All references must resolve before accepting a document.

Add a required navigationDesignId to Navigation elements in the new version. Migration creates a deterministic Main navigation design from the old array and assigns every old Navigation element to it. Schema 10 requires the old array to be empty and all element references to resolve. Schema 9 rejects design fields and references. Migration must be idempotent and must not mutate old immutable revision bytes or checksums. Historical revisions migrate when read.

Deletion validates usage across all pages. Reject deletion while any element references a design. Render unresolved references defensively without silently choosing an unrelated menu; schema validation remains the save/publish boundary. Reuse ordinary revision persistence and canonicalization; do not introduce a separate Navigation history or database table.

Proposed workspace

Add Navigation alongside Layout, Forms and Library. Use a design picker, name field, usage list, selected menu-item editor and representative preview. Keep the menu outline readable; edit one selected item rather than stacking every destination field on screen. Native buttons move items earlier/later, a parent selector nests or promotes eligible items, and Remove has an explicit accessible name. A parent with children cannot itself become a child. Dragging uses the same validated move operation as the buttons and parent selector.

Announce completed moves and removals; restore focus by stable item ID. Keep invalid local destination text visible with associated guidance. A design selection is UI state and creates no revision. Completed edits use the existing navigation action context and autosave status. Preview uses the actual site renderer, isolated from Builder controls, with navigation clicks contained. The Layout inspector offers a design selector and an Edit design route; presentation and grid controls remain local to the element.
