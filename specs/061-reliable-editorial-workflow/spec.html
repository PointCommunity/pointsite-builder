Issue #61: Reliable autosave and cloud publishing

Owning Issue and approved product requirements. Research captured September 12, 2026; this is the implementation specification, not a completion report.

T1 is in progress. Contracts are not frozen. No application code, database migration, permission setting, or deployed content has changed. GitHub installation details require the account holder to complete its “Confirm access” screen. Finish that inventory and the storage rehearsal before dependent implementation. All T2–T14 acceptance evidence remains pending.

Objective and preserved boundaries

Deliver browser-only editorial operation: independent remote drafts, logical-action autosave, pending-only refresh recovery, cloud Staging jobs, exact Staging acceptance, Administrator-only Production promotion, and cloud retry/rollback. Builder itself keeps its single Production environment and local software QA. Actual public content publication still requires an explicitly selected and approved candidate.

  • Keep Cloudflare Workers/D1 and GitHub. No paid capacity, new paid service, homelab, or public private-data backup.
  • Preserve the existing 90-day automatic revision minimum, named history, immutable checksums, attribution, and immediate whole-draft purge. Do not shorten retention to make a forecast pass.
  • Preserve foreground checkout availability within five seconds, warning at 25 minutes, expiry at 30 minutes, and safe device transfer. Passive traffic must not renew authority.
  • Only pending editing payloads and minimum non-secret recovery metadata persist in the browser. Browser storage cannot grant a role, lease, or revision authority.
  • Keep Issue #57 and unrelated repository changes outside this work. Do not publish fixture content to Staging or Production merely to test the implementation.

Proposed workload and numeric gates

These are declared test scenarios, not claims about real usage. Fix their final values after T1 rehearsal; any revision must retain the observed high-activity case and explain the change.

  • Reference day: two editors, two 45-minute sessions each, 100 completed actions per session: 400 saves/day. Per session: 20 Library listings, ten dashboard refreshes, four history visits, continuous foreground checkout observation. Ten Staging jobs/day, two Production promotions/day, and one rollback rehearsal in an isolated fixture.
  • Reference corpus: 12 drafts, 100 media entries/draft, 800 starting revisions, then 36,000 additional revisions for a 90-day projection. Published candidates include more than the old upload batch size. Model 10% request retries, uncertain acknowledgements, two duplicate dispatches, one runner interruption, and maintenance separately.
  • Growth case: four editors, four such sessions each: 1,600 saves/day. Measure and report whether this fits; do not silently redefine it as the supported reference workload or promise unlimited use.
  • Account targets: at most 3,500,000 D1 reads/day, 70,000 writes/day, 70,000 Worker requests/day, and 350 MB allocated in the Builder database. Reserve at least 30% of documented allowances; include other account consumers, monitoring, Staging authentication, retries, indexes, and maintenance. Use 500,000,000 bytes conservatively for the documented 500 MB database limit.
  • GitHub target: below 70% of the verified installation's actual primary rate limit, honoring secondary limits and Retry-After. Standard public-repository runners only. Proposed artifact retention: one day for transient output; published Git content and verified reproducible manifests provide durable candidate inputs. No Actions cache is required by this design.
  • Storage feasibility is a gate: 400 × 90 × 81,730 is 2.94 GB before overhead. Even independent gzip snapshots project 462.5 MB before media and indexes. Merely deleting duplicate retry responses does not establish 90-day suitability.

R2–R5, R12–R13 Editing writes an ordered pending journal, then marks local persistence complete. A completed action enters the single remote queue; the receipt removes only that acknowledged action. Recovery authenticates, obtains current backend authority, reconciles exact action receipts, then sends unchanged identities. Remote drift or lost checkout blocks replay. Acknowledgements never replace newer pending content. Refresh before/after storage commit, before/after remote commit and acknowledgement; storage denied, corrupt data, wrong user/draft, old client, newer revision, and lost acknowledgement.
