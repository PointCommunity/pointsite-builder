Objective and preserved boundaries

Deliver browser-only editorial operation: independent remote drafts, logical-action autosave, pending-only refresh recovery, cloud Staging jobs, exact Staging acceptance, Administrator-only Production promotion, and cloud retry/rollback. Builder itself keeps its single Production environment and local software QA. Actual public content publication still requires an explicitly selected and approved candidate.

  • Keep Cloudflare Workers/D1 and GitHub. No paid capacity, new paid service, homelab, or public private-data backup.
  • Preserve the existing 90-day automatic revision minimum, named history, immutable checksums, attribution, and immediate whole-draft purge. Do not shorten retention to make a forecast pass.
  • Preserve foreground checkout availability within five seconds, warning at 25 minutes, expiry at 30 minutes, and safe device transfer. Passive traffic must not renew authority.
  • Only pending editing payloads and minimum non-secret recovery metadata persist in the browser. Browser storage cannot grant a role, lease, or revision authority.
  • Keep Issue #57 and unrelated repository changes outside this work. Do not publish fixture content to Staging or Production merely to test the implementation.

Workload and numeric gates

These are fixed declared test scenarios, not claims about real usage. Any revision must retain the observed high-activity case and explain the change. Free allowances are the PM's operating constraint; missing live plan access cannot authorize paid resources or a claim of verified suitability.

  • Reference day: two editors, two 45-minute sessions each, 100 completed actions per session: 400 saves/day. Per session: 20 Library listings, ten dashboard refreshes, four history visits, continuous foreground checkout observation. Ten Staging jobs/day, two Production promotions/day, and one rollback rehearsal in an isolated fixture.
  • Reference corpus: 12 drafts, 100 media entries/draft, 800 starting revisions, then 36,000 additional revisions for a 90-day projection. Published candidates include more than the old upload batch size. Model 10% request retries, uncertain acknowledgements, two duplicate dispatches, one runner interruption, and maintenance separately.
  • Growth case: four editors, four such sessions each: 1,600 saves/day. Measure and report whether this fits; do not silently redefine it as the supported reference workload or promise unlimited use.
  • Account targets: at most 3,500,000 D1 reads/day, 70,000 writes/day, 70,000 Worker requests/day, and 350 MB allocated in the Builder database. Reserve at least 30% of documented allowances; include other account consumers, monitoring, Staging authentication, retries, indexes, and maintenance. Use 500,000,000 bytes conservatively for the documented 500 MB database limit.
  • GitHub target: below 70% of the verified installation's actual primary rate limit, honoring secondary limits and Retry-After. Standard public-repository runners only. Proposed artifact retention: one day for transient output; published Git content and verified reproducible manifests provide durable candidate inputs. No Actions cache is required by this design.
  • Storage feasibility is a gate: 400 × 90 × 81,730 is 2.94 GB before overhead. Even independent gzip snapshots project 462.5 MB before media and indexes. Merely deleting duplicate retry responses does not establish 90-day suitability.

T1 decisions and rollout gates

  • Verified installation: checks and metadata read; code read/write; all organization repositories. Use repository_dispatch, which requires existing Contents write, rather than requesting Actions write. Mint installation tokens for only the selected repository and necessary permissions. Preserve installation settings.
  • The runnable forward fixture is npx tsx tests/performance/editorial-workload.ts. All 400 reconstructions passed, including Unicode. Modeled storage averaged 1,565 bytes/action, projecting 56.34 MB of 90-day revisions and 190.34 MB including declared media/metadata budgets. This supports prototyping; it does not replace real D1 allocation or CPU evidence. The 1,600-action growth case projects 359.36 MB including those budgets, exceeding the reference headroom target.
  • Encoding references one full checkpoint directly, never an unbounded delta chain. Create a checkpoint at most every 32 revisions; each read needs its own record and at most one checkpoint. Validate lengths, offsets, codec version, ownership and canonical checksum before returning data. Use a full snapshot when it is smaller. Retention pins required checkpoints; retain conservative references until reconstruction and bounded projection rebuilding succeed. A reader-compatible bridge precedes enabling encoding.
  • Library projections contain retained item signatures/dates and source paths per draft, not one row per item per revision. Changed signatures update dates; unchanged signatures add no item writes. Each save advances one sequence cursor. Backfill processes at most eight revisions per call (25 statements including its concurrency guard). Retention invalidates coverage and rebuilds it before Library deletion can resume; missing coverage fails closed without a GET-time backfill.
  • Save requests carry expected revision ID, checksum, ordered action ID and current checkout. The transactional receipt binds actor, draft, complete request hash and result revision. Reuse with different input fails. Replay is resolved before stale-base rejection but after current authority validation. Compact receipts are retained for 90 days; older requests still fail their immutable expected revision. No-op receipts prevent uncertain acknowledgement from creating revisions.
  • Cloud endpoints accept only short-lived GitHub OIDC credentials plus a dispatch nonce. Pin repository, workflow path, workflow commit, event, audience, run ID and attempt. A compare-and-swap claim allows one runner. Candidate read endpoints expose only the job's immutable revision and pinned media. Runner callbacks are claims to verify against exact run, commit, manifest and live output, never arbitrary success authority.
  • Store content-free deletion receipts and recovery coordination in a separate small D1 database, outside the workspace Time Travel rewind. This uses the existing D1 service and free account allowance; no paid resource is permitted. Write a receipt before purge and fail closed on receipt-store failure. Recovery closes workspace access, restores a selected bookmark, reapplies receipts in bounded batches, verifies, then reopens. Runtime D1 recovery credentials and the extra binding require explicit configuration review before deployment.
  • Provider telemetry uses a read-only runtime credential. If absent, show unknown; do not substitute local audit counts. Existing local CLI access can read D1 usage. Direct API checks on 12 September 2026 returned HTTP 200 for Worker settings, database metadata and a read-only SELECT 1 query (zero rows written). Subscription readback returned HTTP 403. Dashboard access is not required to continue implementation or those operational checks. Measure the defined workload against documented free allowances; billing details are not a release prerequisite. Runtime credential configuration remains necessary for provider sampling. Cloudflare credentials do not replace the Builder's authenticated user session, and missing measurements must remain unknown.

Implementation order and verification

Save-integrity increment: version request hashes in the existing receipt table. Bind the complete semantic request, including expected revision and label, while excluding transport request IDs and renewable checkout tokens. Validate current checkout before replay, resolve a matching receipt before stale-base rejection, persist no-op receipts without a revision or audit event, and return the winning receipt after a simultaneous identical request. Retain new receipts for 90 days and reject expired identities rather than reusing them. Legacy receipts retain their original hash contract and must not bypass draft or label matching. The browser sends the exact base revision and preserves it through retries. Tests cover altered input, repeated content with a different revision, lost acknowledgement, concurrent retry, no-op, expired receipt, and revoked checkout. Receipt payload compaction and role revocation at the transaction boundary remain separate pending work.

Passive view-state persistence sends activity=false. Checkout validation and context writes share one transaction; identical context does not rewrite its timestamp or content. Passive context, connectivity and focus events do not extend the 30-minute lease. Visible pointer, touch and keyboard input remain genuine activity, with the existing four-second availability checks preserved. Old clients may omit activity and the revision header during the compatible rollout; updated clients always send both. Full enforcement for old clients remains pending.
