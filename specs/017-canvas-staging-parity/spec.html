Spec 017 · GitHub Issue #25

Trustworthy canvas and protected-Staging parity

Objective

Give PointSite authors one deterministic, grid-backed composition model. At a matching viewport, the editing canvas geometry (excluding authoring chrome), standalone preview, and protected Staging renderer must interpret the exact saved revision identically. A visible insertion phantom must represent the actual proposed cells and must never hide collision fallback.

Users and scenarios

  • Authors drag any supported element into any visible, unoccupied grid cells and see its type, coordinates, footprint, and validity before release.
  • Keyboard authors move and resize selected elements by grid cell with announced blocked states.
  • Publishers receive a safe preflight failure before Staging changes if any canonical renderer source or stylesheet differs.
  • Existing compatibility and flow sections keep their rendered appearance until an author explicitly converts them; new pages and sections remain grid-backed by default.

Canonical contracts

  • Rendering: SiteFrame, SiteRenderer, the registry, tokens, schema, migrations, layout functions, and site.css are the canonical site-kit.
  • Identity: schema and semantic renderer version are necessary but insufficient. Builder pins the Git blob identity of every file synchronized to protected Staging and verifies those paths at the exact expected Staging base commit before creating candidate blobs or commits.
  • Geometry: twelve columns; coordinates are one-based; the active responsive breakpoint falls back to desktop only when no explicit override exists; snapping and bounds use the measured grid surface after iframe scaling.
  • Collision: an occupied target is invalid. The phantom remains at the pointed cells, is labeled invalid in text and pattern, and releasing it persists no element. There is no automatic relocation.

Responsive and accessibility requirements

  • Supported authoring viewports are phone 360 px, tablet 768 px, and desktop 1280 px, plus zoomed and scrolled states.
  • Valid and invalid states use text and shape/pattern, not color alone; motion respects prefers-reduced-motion.
  • Dragging has the existing keyboard/grid-inspector alternative. Move/resize failures and rejected drops use restrained polite status messages.
  • Authoring controls, guides, and phantoms are absent from standalone preview and published markup.

Compatibility and failure behavior

  • No automatic schema migration changes compatibility or flow layout into grid. Explicit conversion uses existing deterministic placement data and remains undoable.
  • A renderer contract mismatch fails with STAGING_RENDERER_MISMATCH before GitHub write calls. Base drift continues to fail with STAGING_BASE_DRIFT.
  • No credentials, draft content, private media, or protected access details are included in mismatch diagnostics.

Project structure and commands

  • Client: src/client/editor; canonical renderer: src/site-kit; publication: src/server/publish and src/server/github; tests: tests/unit, tests/integration, and tests/e2e.
  • Focused: npm test -- --run tests/unit/grid-drag-preview.test.ts tests/unit/github-client.test.ts tests/integration/publish-service.test.ts.
  • Complete: npm run check, npm run test:performance, npm run test:e2e, and git diff --check.

Boundaries

  • Always: preserve exact saved data, verify renderer identity at the expected base SHA, test RED then GREEN, and retain pointer plus keyboard operation.
  • Ask first: Issue-body changes, dependencies, destructive schema/data work, or public PointSite publication.
  • Never: silently relocate a blocked drop, mutate the dirty local Staging checkout, leak authoring chrome, weaken authentication, or deploy public Production PointSite.

Success criteria

  • Tests prove pointed geometry is the phantom and persisted geometry for valid drops, while invalid drops persist nothing.
  • Renderer-contract tests prove every synchronized source file matches Staging at the exact base commit and mismatch prevents writes.
  • Canvas and standalone preview share the same renderer and site CSS; representative visual/browser checks cover phone, tablet, desktop, scroll, zoom, existing content, and all element categories.
  • Save, reload, reopen, and publish preserve grid data; staging verification accepts the exact candidate; public Production PointSite is unchanged.

Regression amendment: explicit desktop grid starts

  • A grid element with a non-default desktop starting column renders on that exact line in the editing canvas, standalone Preview, static Staging output, and protected Staging.
  • Grid placement classes must not override the responsive custom-property contract with span-only auto-placement. Flow layout may retain its legacy span behavior.
  • Browser verification compares geometry only at equal measured viewport widths: 1280 px desktop, 768 px tablet, and 360 px phone. Preview scaling is presentation-only and cannot change the iframe's layout viewport.
  • Representative Header, Hero, and ordinary section elements retain saved coordinates, sizes, content wrapping, and overflow behavior without authoring chrome in Preview or Staging.

Open questions

None. Issue #25 defines the product boundaries, the repository supplies the canonical 16-file renderer sync list, and the existing grid inspector supplies the non-drag interaction.
