PointSite Builder · Spec 015 · GitHub Issue #18

Guided, resumable Staging publishing

Turn one exact saved Builder revision into an officially accepted Staging candidate through a plain-language, recoverable workflow. Publishers and Administrators stay inside the Builder for decisions; GitHub remains optional technical evidence.

Assumptions accepted from Issue #18 and live evidence

  1. The review destination is the protected https://staging.pointatx.org.
  2. Existing D1 publish jobs and immutable approvals are authoritative; no migration is required.
  3. Automatic verification polls every 10 seconds while pending and pauses after 15 minutes.
  4. Draft-revision drift or a Staging head different from the candidate commit makes the workflow stale.
  5. A stable revision-and-base idempotency key makes repeat submissions converge on one job.

Objective

A Publisher or Administrator can open Publish, understand the full five-step path, start one exact publication, leave, return, watch verification advance automatically, review the protected site, and deliberately accept the exact candidate. Every failure names a safe recovery action and the interface always states that Production is unchanged.

Lifecycle contract

  1. Ready: saved revision and current Staging base are known; Publish is available.
  2. Publishing: one durable job is queued or running; duplicate publication is locked.
  3. Verifying: the exact commit exists and Builder follows required checks and deployment.
  4. Review ready: all evidence passed; the protected Staging link and acceptance action are available.
  5. Accepted: immutable approval identifies the official Staging candidate; Production is unchanged.

Failed publish, failed verification, timed-out monitoring, unavailable status, and stale candidates are explicit states with retry, refresh, review, or republish guidance.

Functional requirements

  • FR-015-001: Show the complete lifecycle, current step, completed steps, and next action before publication.
  • FR-015-002: Restore the latest applicable durable job and approval by draft on dialog reopen and full reload.
  • FR-015-003: Require exact revision ID and checksum on publish; reject revision drift server-side.
  • FR-015-004: Reuse one idempotent job for the same revision, candidate, and Staging base.
  • FR-015-005: Poll verification at a bounded interval only while pending; pause after the bounded window and retain manual refresh.
  • FR-015-006: Persist verification evidence and audit only when its state or evidence changes.
  • FR-015-007: Keep commit hashes, checksums, and GitHub links inside optional technical details.
  • FR-015-008: Offer a clear link to review protected Staging before the deliberate acceptance action.
  • FR-015-009: Lock acceptance unless mandatory evidence passes and current Staging still equals the exact candidate commit.
  • FR-015-010: Make ready, publishing, verifying, review-ready, accepted, failed, paused, unavailable, and stale states non-color-dependent and actionable.
  • FR-015-011: Recheck Publisher or Administrator role plus current GitHub write authority on publish, refresh, restore, and acceptance APIs.
  • FR-015-012: Never write the public PointSite repository or imply that Staging acceptance changed Production.

Tech stack and project structure

React 19, TypeScript 5.9, Hono, D1, Zod, Vitest, Testing Library, Playwright, and GitHub App installation APIs.

  • src/server/publish/ — durable job recovery, deduplication, and verification observation.
  • src/server/approvals/ — immutable acceptance recovery and exact-candidate enforcement.
  • src/client/publish/ — lifecycle derivation, bounded polling, accessible progression, and recovery copy.
  • tests/unit, tests/integration, tests/e2e — transition, persistence, authorization, drift, retry, browser, and accessibility proof.

Testing strategy

  • RED first for each lifecycle phase, latest-job restoration, changed revision, Staging drift, idempotent replay, and unchanged-evidence audit suppression.
  • Integration coverage for API authorization, sanitized workflow snapshots, approval recovery, exact-revision conflicts, and stale-candidate rejection.
  • Browser coverage for immediate pass, prolonged pending, verification failure, close/reopen, reload, stale revision, monitoring pause/manual refresh, and accepted completion.
  • Hands-on keyboard, focus, responsive, live-region, protected-link, production-lock, and deployed restoration checks.

Boundaries

Always: preserve current roles, exact-candidate checks, auditability, protected Staging, and the static public-site boundary.

Ask first: changing role policy, adding a deployment environment, weakening Cloudflare Access, adding credentials, or enabling Production promotion.

Never: trust client state for permission, expose tokens/private draft payloads, accept after drift/failure, or write public PointSite.

Success criteria and open questions

Every Issue #18 acceptance criterion is mapped to automated or hands-on evidence, the full repository gate passes, exact-head GitHub Quality passes, and deployed Builder production resumes a real protected Staging workflow without any public PointSite change.

Open questions: None. The Issue body, repository policy, live configuration, and existing contracts resolve the implementation decisions.
