Guided Staging publishing research

Confirmed current behavior

  • StagingPublish keeps job/result/approval only in mounted React state.
  • The user must press “Check staging verification”; each press writes evidence and an audit event even when nothing changed.
  • The original Publish action remains available after the exact commit is created.
  • D1 already stores candidate draft/revision identity, job status/result/evidence, and immutable approvals.
  • The protected review URL is live at staging.pointatx.org and returns 401 without Cloudflare Access.
  • Staging exposes exact-commit GitHub checks named verify and deploy.

State and recovery decision

Problem Decision
Mounted-only identity Read the latest durable job by draft and recover its latest approval.
Duplicate publication Bind the request to exact revision ID/checksum and derive one stable idempotency key from revision plus base.
Manual-only verification Poll every 10 seconds while pending, stop on terminal state, and pause after 15 minutes.
Audit noise Persist and audit verification only when serialized evidence changes.
Candidate drift Compare selected revision with the stored candidate and current Staging head with its result commit.
External operational jargon Primary UI uses five plain-language steps; technical identifiers remain in a disclosure.

GitHub evidence model

GitHub check runs expose queued/in-progress/completed states and terminal conclusions including success, failure, cancelled, timed out, skipped, and stale. Deployment statuses similarly progress through pending/in-progress to success or failure. The Builder can therefore map the existing exact-commit verify and deploy checks into pending, failed, and passed without asking users to interpret GitHub.

  • GitHub REST API: check runs
  • GitHub guide: checks state and conclusions
  • GitHub REST API: deployment statuses
  • GitHub REST API rate limits

Security and privacy

  • Every recovery, refresh, publication, and acceptance route retains server-side role plus live repository-permission checks.
  • The resume response omits idempotency keys and private document content.
  • Automatic updates are bounded, do not run in hidden/unmounted workflows, and stop on terminal state.
  • Acceptance rechecks current Staging head immediately before recording the immutable decision.
  • No Production API or public-repository write is added.
