Linode Production release contract

The Builder Production command must deploy only to the Linode at 45.33.2.134. Canary remains on homelab GitOps. The old homelab Production command must fail closed.

Release identity and gates

  1. Use clean, pushed source and passing GitHub Quality. Match the approved Canary Git tree, digest, healthy Argo revision, and recorded approval. A merge commit may differ from the Canary commit only when its Git tree is identical.
  2. Bind approval to the Linode target and observed wrapper and service-unit hashes. Recheck those hashes immediately before changing the host.
  3. Require trusted SSH host identity, healthy current service, separate mounted backup storage, and a fresh successful native backup before changing source or the wrapper.
  4. Build the merged source on Linode for linux/amd64 in a pinned Node build container, verify its native release metadata, then package the runtime image. Change only the pinned image tag, restart, and verify local health, source identity, mounts, recovery, a new backup, and both public routes. Restore the prior tag and restart if a post-switch gate fails.

Commands and layout

npm run release:build and npm run release:canary retain homelab Canary behavior. npm run release:inspect -- --candidate FILE produces the Linode configuration hash for exact approval. npm run release:production -- --candidate FILE --approval FILE performs the guarded Linode release. The local orchestrator is scripts/release-linode.mjs; the host procedure is scripts/deploy-linode-production.sh.

Verification and limits

Run release contract tests, the skill-alignment audit, and full local QA. A local test cannot prove live Linode access or authenticated workspace behavior. The deploying agent must verify those live gates and report any unavailable evidence. No current application candidate is approved by this infrastructure change.
