Action-based autosave

Persist every completed authoring action as one attributable immutable revision without a global Save button, while preserving meaningful undo, redo, conflict protection, offline recovery, and quiet accessible feedback.

Objective

An Editor changes any part of an active draft and can trust that each completed logical action is queued, saved in order, acknowledged by the server, and represented in History and administrative audit activity. The interface never calls pending work saved and never requires a routine manual draft save.

User stories and acceptance scenarios

P1 · Edit without a Save button

  1. Given an editable active draft, when the user completes a discrete add, remove, duplicate, reorder, move, resize, drop, control, undo, or redo action, then that changed document is queued immediately and eventually becomes one server-acknowledged revision and audit event.
  2. Given a text field, when typing pauses for one second or focus leaves the field, then the complete edit becomes one logical action instead of one revision per keystroke.
  3. Given any editable workspace, then the upper-right global Save button is absent and specialized media-detail and revision-label save controls remain unchanged.

P1 · Preserve rapid and interrupted work

  1. Given one save in flight, when later actions complete, then they remain locally visible, retain order, and save after the acknowledgement without being replaced by the older response.
  2. Given a transient failure, when connectivity remains available, then the same idempotent action retries after bounded delays of one, two, and four seconds before waiting for a deliberate retry.
  3. Given an offline client, when connectivity returns, then pending actions resume in order without a retry loop while offline.
  4. Given a revision conflict or validation failure, then pending local work remains visible and unsaved, automatic retries stop, and safe recovery actions are explained.

P2 · Understand saved history

  1. Given a successful action save, then History identifies the actor, time, revision number, action category, and safe editing surface.
  2. Given an Administrator viewing audit activity, then the same category, safe context, and completed result are visible without content values or technical identifiers.
  3. Given an unchanged document checksum, then the action is acknowledged without creating a revision or audit event.

Logical-action contract

Interaction Completion boundary Category
Text, textarea, URL, email, telephone, and numeric entry One second without another change in that action, or field blur text-edit
Select, checkbox, color, preset, and other discrete controls Accepted control change control-change
Add, remove, duplicate, and ordered-list controls Completed button or keyboard operation add, remove, duplicate, or reorder
Canvas insert, drop, move, reorder, and replacement One recorded editor action after the final drop add, move, reorder, or replace
Pointer or keyboard grid movement and resizing Final recorded move/resize; transient pointer frames never persist move or resize
Undo and redo Completed history navigation undo or redo
Revision restoration Server-confirmed restore as a new immutable revision restore

Context is selected from the content-free set: page content, page details, page structure, forms, library attachment, linked media, navigation, theme, site settings, collections, section settings, element settings, element layout, and revision history. Edited values, field contents, page or element identifiers, checksums, tokens, and raw documents are never action metadata.

Functional requirements

  • FR-016-001: Remove the global draft Save button from every editable workspace.
  • FR-016-002: Require every draft-document mutation to supply a finite action category and safe context and to follow the defined completion boundary.
  • FR-016-003: Coalesce only continuing text entry within one pending action; a blur, different action, or elapsed one-second pause closes that action.
  • FR-016-004: Serialize persistence so at most one save request is in flight for the client and later snapshots retain order.
  • FR-016-005: Never apply an older acknowledgement over newer local state; use it only to advance the authoritative revision base for the next queued action.
  • FR-016-006: Give every logical action one stable idempotency key across retries and preserve compare-and-swap checksum protection.
  • FR-016-007: Retry transient failures at most three times with bounded backoff; pause offline; stop on conflict or validation failure; retain a manual Retry autosave recovery action.
  • FR-016-008: Bound the in-memory queue to 250 completed actions. When full, preserve queued and acknowledged work, reject further document mutation, and instruct the user to reconnect or resolve the save failure.
  • FR-016-009: Prevent navigation back to All drafts while actions are pending, saving, offline, conflicted, invalid, or failed; allow departure after the queue is acknowledged or explicitly discarded after copying recovery data.
  • FR-016-010: Validate category and context server-side; atomically advance the draft, insert one immutable revision, append one audit event, and retain idempotency.
  • FR-016-011: Store category and safe context on new revisions; existing revisions remain readable with a neutral legacy fallback.
  • FR-016-012: Suppress revision and audit creation when the canonical document checksum matches the current revision.
  • FR-016-013: Preserve the editor's undo and redo controls and save their resulting documents as new undo and redo revisions.
  • FR-016-014: Keep visible pending, saving, saved, offline, retrying, conflict, validation, and terminal error states without relying on color.
  • FR-016-015: Use polite status announcements only for logical-action and persistence transitions; use an alert for conflict, validation, queue-limit, and terminal failures; never announce individual keystrokes or pointer frames.
  • FR-016-016: Keep specialized media-detail and revision-label save operations unchanged because they do not mutate the draft document.
  • FR-016-017: Reject a canonical serialized document larger than 1,500,000 bytes before D1 persistence, retain the pending action, and explain that the draft must be reduced before retrying.

Security and privacy

  • Authorization, schema validation, rate limiting, idempotency, and compare-and-swap remain server-side.
  • Action metadata uses server-validated enums and contains no user-authored values.
  • Automatic retries reuse one key, stop after the bounded schedule, and never retry conflicts.
  • Client logs and audit events contain no draft payloads, private media, credentials, or tokens.

Capacity and performance success criteria

  • SC-016-001: One logical action creates at most one Worker mutation request and one four-statement transactional D1 batch unless a bounded retry is required.
  • SC-016-002: The modeled expected workload of 50 completed actions per day uses no more than 0.05% of the 100,000 daily Worker request allowance and remains below 1% even if every action consumes all three retries.
  • SC-016-003: At the measured 65.9 KiB reference document size, 50 daily revisions retain about 289.6 MiB over 90 days, below the 350 MiB warning threshold and 500 MiB per-database free limit; the live capacity meter continues warning at 70%.
  • SC-016-004: Queue processing adds less than 100 ms of client interaction overhead and the repository's 1,000-request API performance test remains below 100 ms p95.
  • SC-016-005: Automated tests prove zero lost or reordered actions during rapid input, in-flight edits, offline recovery, retry, conflict, validation, undo, and redo.

Out of scope

  • Draft checkout, inactivity expiry, cross-device editor restoration, or durable offline storage.
  • Removing or redesigning Save details for media metadata or Save label for revisions.
  • Publishing public content, changing protected Staging, or enabling Production promotion.
