PointSite Builder Development Pipeline

Objective

Establish one complete, repository-owned development pipeline for PointCommunity/pointsite-builder. The pipeline will use a private organization GitHub Project modeled on Zuriel-Labs/versa, portable agent skills, deterministic checks, local hands-on validation, and direct deployment of an exact verified revision to https://builder.pointatx.org.

Confirmed assumptions

  • The Project owner is the PointCommunity organization.
  • The Project title is PointSite Builder Development and it remains private.
  • Versa supplies the Project schema, views, built-in workflows, one-active-Issue invariant, agent-owned metadata movement, canonical-skill layout, and cross-agent adapters.
  • Builder deliberately diverges from Versa at release: there is no Builder Staging or Canary. Local QA and exact-head GitHub Quality lead directly to Builder production.
  • The Builder's separate ability to publish public-site content to PointCommunity/pointsite-staging is a product workflow, not a Builder deployment environment.

GitHub Project contract

Concern Required configuration
Status Backlog, On Hold, In Progress, In Review, Done
Active In Progress or In Review; one Issue maximum across both
Priority P0, P1, P2, P3
Impact High, Medium, Low
Effort XS, S, M, L, XL
Views Backlog Priorities and Kanban board views grouped by Status
Built-in workflows Keep Item added → Backlog, linked pull request → In Progress, item closed → Done, Done → close Issue, and sub-issue addition enabled. Disable pull request merged → Done because merge alone is not Builder completion.
Repository Link only PointCommunity/pointsite-builder.

Every open Builder Issue must be in the Project with complete Status, Priority, Impact, and Effort values. Existing Issue #18 is onboarded through Backlog and initially classified as P1, High impact, and M effort based on its approved Issue body. Any later, independently selected work transition must be preserved when it satisfies the governed active-Issue contract.

Issue and label model

Each governed Issue has exactly one type:* label and at least one relevant area:* label. The Builder taxonomy covers defects, features, maintenance, security, authoring, data, deployment, documentation, identity, media, publishing, UI, and workflow. Existing generic GitHub labels remain available for compatibility, but the governed pipeline uses the namespaced labels.

State flow

  1. An approved Issue is created open and unassigned, added to the Project, fully classified, and set to Backlog.
  2. PM selection moves it to In Progress and assigns only brimdor.
  3. Implementation occurs on issue/<number>-<slug> with specification, tests, and a PR containing Refs #<number>.
  4. Agent QA includes full repository gates and hands-on local browser checks. A verified exact PR head moves to In Review.
  5. Unless the PM requested an earlier stop, the verified PR is squash-merged and the merge tree must equal the reviewed tree.
  6. The exact clean origin/main commit must pass GitHub Quality, then deploy directly to Builder production.
  7. Only verified live production permits Issue closure, unassignment, and Project Status Done.
  8. On a production failure, restore the recorded Cloudflare version, keep the Issue open and active, and remediate through a reviewable change.

Commands

  • npm run skills:check validates skill registries, adapters, policy, Project contract scripts, and release helpers.
  • npm run pipeline:health performs a read-only live audit of Git, Issues, Project metadata, PR linkage, and CI.
  • npm run check runs skill alignment, formatting, types, lint, contracts, runbooks, coverage, and build.
  • npm run test:performance and npm run test:e2e remain required release gates.
  • npm run deploy deploys only a clean, pushed, exact origin/main revision.
  • npm run verify:live checks production health, HTML, and HTML-derived assets.

Testing strategy

  • Unit-test pipeline snapshot logic, health payloads, HTML validation, and asset extraction.
  • Validate every canonical skill and regular-file adapter.
  • Run the alignment audit, formatter, TypeScript, lint, contracts, runbooks, coverage, build, performance, and browser suites.
  • Run the live pipeline audit after GitHub setup and compare the Project schema, repository link, workflows, views, open cards, labels, assignments, and PR linkage.
  • Do not deploy production for this governance-only change unless the change is merged through the newly established Issue pipeline.

Boundaries

  • Always preserve unknown user-owned changes and commit only task-owned files.
  • Always read back GitHub mutations and verify exact live state.
  • Always keep Builder deployment separate from public PointSite publishing.
  • Ask first before destructive schema/data recovery or expanding this Project to another repository.
  • Never create a Builder Canary or Builder Staging environment.
  • Never close an Issue on merge alone.
  • Never weaken authentication or expose credentials to manufacture release evidence.

Platform limitation

GitHub currently returns a plan-level error when branch protection or repository rulesets are requested for this private repository. Until the organization plan changes, the repository skills and health audit must enforce and report the PR, exact-tree, and Quality requirements; they must not claim GitHub is enforcing unavailable branch rules.
