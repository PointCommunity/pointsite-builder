Issue 37: independent responsive layouts

Source of truth: GitHub Issue #37, “Persist Hero text resizing and remove the canvas Move badge.”

Objective

Make each completed Hero Heading or Body width resize one durable, ordered autosave action whose exact clamped value survives navigation, refresh, draft reopen, repository validation, revision storage, Preview, and protected Staging rendering. Remove only the visible Move pill while preserving the full move control and all pointer, keyboard, focus, announcement, collision, resize, and selection behavior.

PM production finding, 2026-09-09: Phone, Tablet, and Desktop are independent layout canvases. An element's grid position, grid size, vertical placement, and Hero Heading or Body width may differ in each view. The element tree and element content remain shared, so adding, removing, duplicating, or editing an element continues to affect all three views.

Assumptions confirmed by repository evidence

  • The existing integer range of 30 through 100 and keyboard step sizes remain authoritative.
  • SiteDocument, immutable revisions, checksums, and compare-and-swap remain the persistence source of truth. Schema version 9 will make all three layout values explicit; browser-only storage is not used.
  • Pointer-move frames stay transient. Pointer release or keyboard input creates the durable resize action.
  • The semantic move button remains present and focusable; only its visible child label is removed.
  • The PM production finding supersedes the original exclusion of breakpoint-specific Hero widths for this remediation cycle.

Responsive ownership contract

  • Independent per view: grid column, row, column span, row span, placement alignment, Hero Heading width, and Hero Body width.
  • Shared across views: section and element membership, ordering, content, links, media, color/surface, typography choices, and other semantic element settings.
  • New elements receive three explicit, equal starting layouts. Editing any one view changes only that view; there is no inheritance or “Reset to desktop” behavior.
  • Version 8 and older documents migrate without a visual jump by copying each existing effective layout and Hero width into Phone, Tablet, and Desktop values.

Technology and structure

  • React, TypeScript, Puck, Vite, Vitest, Playwright, Hono, D1, and the in-memory repository.
  • Resize interaction and Puck conversion: src/client/editor/VisualEditor.tsx.
  • Move and whole-element resize overlay: src/client/editor/GridOverlay.tsx and src/site-kit/site.css.
  • Autosave ordering: src/client/editor/action-autosave.ts.
  • Schema and rendering: src/site-kit/schema.ts and src/site-kit/registry.tsx.
  • Behavior evidence: focused unit, integration, and tests/e2e/authoring.spec.ts coverage.

  • Repository gates: npm run check, npm run test:performance, npm run test:e2e, npm run skills:check, npm run pipeline:health, and git diff --check.

Testing strategy

  • RED: focused unit and browser coverage must fail on the current branch by asserting that a Phone resize does not change Tablet or Desktop and that all grid layouts are explicit.
  • GREEN: focused interaction coverage proves pointer, keyboard, cancel, delayed acknowledgement, consecutive actions, view switching, and checkout close/reopen behavior.
  • Repository tests prove all responsive width and placement fields survive schema parsing, checksum calculation, memory and D1 revision insertion, migration, and retrieval.
  • Accessibility coverage proves the visible Move text is absent while the named button, focus indication, keyboard movement, handles, and status region remain.
  • Hands-on local browser checks cover phone, tablet, and desktop before release.

Boundaries

  • Always preserve action ordering, idempotency, validation, checkout ownership, responsive containment, independent view geometry, independent Heading and Body values, and renderer parity.
  • Ask before changing the Issue body, width limits, keyboard steps, or deployment model.
  • Never expose draft content or internal identifiers, create revisions for transient pointer frames, publish the public Production PointSite, or weaken accessibility to hide the Move pill.

Success criteria

  • Every applicable acceptance criterion and verification item in Issue #37 has traceable automated or hands-on evidence.
  • The exact final Heading or Body width is the value saved, checksummed, reloaded, previewed, and published by the existing renderer contract.
  • Moving, resizing, or vertically placing an element in one responsive view leaves the other two views byte-for-byte unchanged.
  • Removing an element in any responsive view removes the one shared element from all three.
  • A cancelled pointer resize restores the starting value and creates no durable revision.
  • No selected grid element displays a Move pill; the move button remains semantically and behaviorally intact.
  • All repository gates and exact-head GitHub Quality pass before release.

Open questions: none. Root cause evidence may refine implementation details without changing product scope.
