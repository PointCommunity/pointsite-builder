Issue 78: Editor-authoritative hero width

Objective and acceptance

Use the approved Issue scope: preserve the Layout editor's visible hero width, background, imagery, text geometry and gutters in Preview and generated publication output. Existing drafts must require no reauthoring. Preserve navigation, adjacent sections, responsive placement, text resizing and actions. Public-site parity requires separately authorized content publication and live verification.

Measured cause

Production Builder's published revision 4 reproduces the reported Who We Are discrepancy. At a measured 1280 CSS pixel iframe viewport, loaded fonts and visual viewport scale 1, both surfaces have a 1280px hero at x=-7.5 and a 1160px page shell at x=52.5 (15px scrollbar). Layout adds a 1160px flex grid-item wrapper with overflow hidden; Preview renders the compatibility hero directly inside the page shell. Only Layout clips the hero background to the intended shell. The editor's wrapper and rendering must remain unchanged.

CSS Values Level 4 defines viewport units; CSS Overflow Level 3 defines clipping. Source evidence: compatibility rendering in src/site-kit/registry.tsx, editor elements in src/client/editor/VisualEditor.tsx, and hero breakout plus grid-item clipping in src/site-kit/site.css.

Plan

The initial Chromium regression failed with Preview painted bounds 0–1280 versus Layout 60–1220 at a 1280px viewport. Reusing the wrapper restores the intended 1160px visible width without changing the hero border box or text. Existing non-hero compatibility sections have independent narrow-screen overflow (17px at 900px in the default fixture); verification compares publication overflow with the pre-fix markup to ensure this change adds none. Editor overlays can also extend the document in Firefox, so painted hero geometry is measured separately.

  1. Add a failing browser regression measuring visible hero bounds, text, imagery, navigation and adjacent content in Layout, Preview and static renderer output from identical fixture content.
  2. Reuse the existing grid-item wrapper for compatibility page heroes in the shared renderer. Do not resize the editor, change saved documents, or redesign hero contents. Verify actual grid/flow heroes retain their existing wrappers.
  3. Synchronize the reviewed renderer into the canonical publication runtime, update its exact blob and runtime identities, and preserve lane-specific publication callers. No schema or document-version change is needed for an equivalent rendering correction.
  4. Run focused regressions, then all local gates sequentially, review and exact-head CI. Deploy the Builder Canary candidate and present specific PM tests. Production promotion requires exact Canary approval; content publication remains an authenticated Administrator action.
