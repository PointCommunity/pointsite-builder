Implementation contract

  1. Server-selected lane. Reuse the existing fixed destination table and select from trusted Builder environment/origin. Unknown configurations fail closed. Browser payloads, content files, and dispatch inputs cannot select arbitrary repositories or hosts.
  2. Complete identity binding. Bind tokens, OIDC subject/repository ID, runner audience, reusable runtime SHA, caller blob, main ref, expected base, accepted Staging job, output manifest, deployment origin, release record, recovery, and rollback to the same lane. Never accept historical Canary records pointing at non-Canary destinations.
  3. Exact acceptance. Recheck the latest unrevoked acceptance, active Administrator, draft/revision, source commit, candidate checksum, media/output digest, workflow identity, and fresh destination base before capture and every consequential runner action. Cross-lane, stale, changed, failed, and unverified candidates are rejected.
  4. Durable execution. Reuse existing publication inputs, promotion lineage, slots, run nonce, idempotency receipts, reconciliation, and release storage. Audit every query for implicit destination assumptions. Introduce a migration only if existing persisted identity cannot support isolation; then specify upgrade and rollback compatibility before editing schema.
  5. Clear UI. Display “Site Canary” or “Site Production,” its destination link, accepted candidate, and truthful progress. Keep Administrator-only public publish/rollback controls. Do not broaden permissions or expose release controls merely because an environment flag changed.
  6. Repository bootstrap. Seed the new destination only with reviewed static files already public in a verified baseline, its manifest, and reviewed maintainer callers. Record exact source and file hashes; exclude live drafts, private media, credentials, inherited Production DNS, and automatic push-trigger publication. Establish a verifiable initial deployment before candidate promotion.
  7. Workflow rollout. Keep reusable implementation in the existing canonical Staging repository. Add fixed repository-to-origin mappings and destination-specific callers. Qualify the new immutable runtime in Canary while existing Production callers remain pinned. After Canary proof and required approval, coordinate Production callers and Builder pins with no active or uncertain jobs; refresh acceptance if the base advances.
  8. Recovery. Capture each destination’s previous verified static release, manifest, commit, deployment, and workflow identity. Retry the same captured candidate only after reconciliation. Rollback must target that same destination and recheck current authority and base. Unknown completion remains uncertain until live proof resolves it.

Read-only inspection confirmed valid stored checksums for two schema-9 revisions, but their schema-10 editor representations had different checksums after the Navigation migration. The repository incorrectly reported the loaded schema version as the saved revision version, hiding the pending upgrade.

Preserve saved revision schema/renderer metadata. Once an active editor owns its checkout and browser recovery has finished, use the existing autosave path to save the upgraded document as a new revision. Pending user edits take precedence. Keep historical bytes, expected-revision guards, checkout checks and publication checksum validation unchanged. No server-side bulk rewrite or agent-initiated editorial publication is part of this repair.

Migration and recovery

Migration 0038 keeps historical Production rows unchanged, adds an instance-filtered release view, scopes previous-release and retention constraints to the stored repository, and records the independently deployed Canary bootstrap. Native upgrade tests preserve existing data and verify each lane retains its latest two releases and their input pins. No schema or data is removed.

The native migration runner commits each migration atomically after foreign-key checks and checks integrity before serving requests. A failed migration remains uncommitted. Once 0038 succeeds, older images reject the unknown migration receipt; a raw previous-image rollback is therefore not compatible. Recovery after that point is forward repair using the complete reviewed migration set, with public publication disabled through GitOps while diagnosing. Preserve workspace/recovery volumes, backups and migration receipts. Never remove receipts or restore a database to make an older image start. Restoring a pre-upgrade backup is destructive to newer edits and requires separate explicit approval.
