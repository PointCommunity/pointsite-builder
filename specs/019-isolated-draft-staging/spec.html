Independent drafts and safe Staging coordination

Make every draft a durable, independent publication workspace while coordinating the one shared protected Staging destination through private preflight evidence and a recoverable, server-authoritative publication lease.

Objective

A Publisher or Administrator can prepare multiple drafts over time, privately validate one exact saved revision, and publish it when the shared Staging slot is available. Replacing the version displayed on Staging never changes another draft or deletes its revisions, validation evidence, publish history, or acceptance history.

Lifecycle and requirements

  1. FR-019-001: Persist each preflight attempt against one draft, revision ID, revision checksum, candidate checksum, schema version, renderer version, and renderer-contract checksum.
  2. FR-019-002: Preflight builds and validates the exact candidate privately and performs no protected Staging or Production write.
  3. FR-019-003: A passed preflight remains current across unrelated draft edits and Staging publications; only selected-revision or renderer-contract drift invalidates it.
  4. FR-019-004: One user action runs a required preflight and proceeds directly to publication when the slot and expected Staging base remain current.
  5. FR-019-005: The server atomically grants at most one queued or running Staging publication lease, regardless of client state or concurrent requests.
  6. FR-019-006: Publication leases expire after 15 minutes and are recovered during the next claim without creating an unbounded queue.
  7. FR-019-007: A busy response performs no Staging write and exposes only phase and safe retry timing—not another draft, revision, content, or operator.
  8. FR-019-008: The Builder automatically checks busy availability at a bounded interval and retains an explicit Check availability action.
  9. FR-019-009: The server rechecks authorization, exact revision, valid preflight, candidate checksum, renderer compatibility, current base, and the publication lease immediately before committing.
  10. FR-019-010: A replaced candidate is described as no longer current on Staging; its source draft and immutable evidence remain valid and eligible for later republication.
  11. FR-019-011: Failures and interruptions release or expire the shared lease and preserve draft-scoped state.
  12. FR-019-012: Every preflight, denied claim, recovered lease, publication, replacement, verification, and acceptance is attributable without logging draft content.
  13. FR-019-013: Publisher and Administrator authorization remains server-enforced; Viewer and Editor access remains unchanged.
  14. FR-019-014: Status, warning, recovery, focus, keyboard, responsive, reduced-motion, and non-color communication meet the existing WCAG 2.2 AA target.
  15. FR-019-015: Builder deployment and testing do not publish or promote the public PointSite.

Commands and project structure

Focused: npx vitest run tests/unit/staging-workflow.test.ts tests/integration/publish-jobs.test.ts tests/integration/publish-service.test.ts

Full: npm run check, npm run test:performance, npm run test:e2e, git diff --check

Schema: npm run db:migrate:local before the reviewed migration is applied remotely.

Server coordination lives under src/server/publish; API contracts under src/server/routes and OpenAPI; UI state under src/client/publish; integration, unit, and browser evidence under tests.

Code and testing conventions

Use strict TypeScript, Zod validation at trust boundaries, prepared D1 statements, append-only evidence, pure lifecycle derivation, plain-language UI copy, and repository formatting. Tests cover state-machine logic first, then real Miniflare D1 coordination, route authorization, and critical browser journeys with multiple drafts.

Boundaries

  • Always: preserve exact revision identity, immutable evidence, idempotency, authorization, safe recovery, and the single shared Staging slot.
  • Ask first: destructive data recovery, changed roles, a new environment, or public PointSite publication.
  • Never: expose private draft data, trust client availability, queue publications silently, write to Production PointSite, or make a preflight mutate Staging.

Success

Automated and hands-on tests prove two independent drafts retain their own exact evidence, concurrent publication attempts yield one lease holder, a busy draft recovers automatically, replaced candidates can be republished, expired leases recover, and public Production remains unchanged.
