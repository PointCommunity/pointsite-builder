Research: isolated draft Staging coordination

Existing evidence

  • publish_jobs.candidate_json already binds jobs to draft and revision, and approvals bind to the exact job and candidate tuple.
  • The current workflow restores only the selected draft's latest job, but readiness exists only transiently inside a publish request.
  • The current partial unique index covers only running; queued work and crashed running rows have no bounded recovery contract.
  • The GitHub client already checks the current main SHA, validates the pinned renderer blobs, restricts candidate paths, and uses a non-force compare-and-swap ref update.
  • The client already polls only while needed, stops after 15 minutes, keeps manual refresh, and derives presentation from a pure lifecycle function.

Decisions

  1. Add append-only draft-scoped preflight records rather than attaching readiness to a mutable draft row.
  2. Fingerprint the pinned renderer contract; do not bind preflight validity to mutable Staging content head.
  3. Retain the existing publish-job evidence and add a bounded lease to the active job instead of creating a separate lock table.
  4. Make claiming atomic in D1 and map uniqueness contention to an expected busy result.
  5. Expose a sanitized availability summary through the existing workflow snapshot; reveal no competing draft identity.
  6. Keep the existing one-click publishing intent: preflight is an internal first stage, not another confirmation gate.

Rejected alternatives

  • One Staging site per draft: conflicts with the approved shared-site boundary.
  • A FIFO publication queue: hides future mutations and is explicitly out of scope.
  • Client-only availability: races and cannot authorize a protected write.
  • Invalidating preflight on every Staging change: unnecessarily couples otherwise independent drafts.
  • An indefinite lock: a Worker or GitHub interruption could permanently block publication.

PM review finding: phone Hero overflow

  • The page Hero retained a full-viewport escape rule after becoming an editable element, while the editor placed it inside a clipped Puck item. Its copy therefore laid out wider than the visible phone canvas.
  • The shared Hero renderer covers standard, homepage, and page variants, making one optional percentage-width contract the smallest consistent solution for canvas, Preview, and protected Staging.
  • Existing grid resize controls change the whole element placement; they do not resize the heading and body boxes inside a Hero, so dedicated text-box controls are required.
