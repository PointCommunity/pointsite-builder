Spec 013 · implementation plan

Editable Page Heroes

Architecture decisions

  1. Document ownership: each non-home Page Hero becomes a normal SiteElement record inside its page sections. SiteFrame retains structural landmarks and the centralized persistent Footer.
  2. No duplicate hero: add pageHero to the existing Hero style union and inspector.
  3. Footer continuity: keep the existing global Footer settings and persistent cross-page rendering unchanged; the Footer is not page content.
  4. Versioned migration: schema 8 removes legacy page visual fields, inserts deterministic elements, and keeps the full 0-to-8 migration chain.
  5. Layout continuity: preserve the current page-hero appearance, global Footer, and non-home content shell while allowing root Hero ordering and section position controls.
  6. Release separation: verify and commit pending Spec 012 independently, then commit Spec 013. Push and deploy the combined exact head once.

Dependency order

RED contracts → schema/migration helpers → renderer → authoring UI → browser verification → release

Phases

Phase Outcome Checkpoint
0. Protect existing work Spec 012 and AGENTS changes are validated and committed without mixing Spec 013. Focused + full required gates for the pending work; clean boundary commit.
1. Contract RED Failing tests prove the static page-hero defect and define v8 migration output. Failures are for missing v8 behavior, not test setup.

3. Rendering Non-home Hero renders only from page blocks; the centralized Footer remains unchanged. All default routes retain semantic content and media.
4. Authoring Page Manager, catalog, inspector, and new-page defaults use registered elements. Component tests and focused browser journey pass.
5. Full verification All repo gates pass on the final tree. Diff review, coverage, cross-browser E2E, performance, audit, and build.
6. Production release Exact pushed head is deployed to Builder production and verified live. GitHub Quality success, Cloudflare deployment readback, health, authenticated browser behavior, zero console errors.

Risks and mitigations

Risk Impact Mitigation
Loss or duplication during v7 migration High Pure deterministic helper, exact-value tests, unique derived IDs, idempotence, all-version chain tests.
Non-home layout changes when chrome enters Puck High Preserve existing classes and shell behavior; visual assertions at desktop/tablet/phone widths.
Centralized Footer behavior changes accidentally Medium Keep Footer rendering and settings outside the page migration; add continuity assertions for every route.
Existing pending edits are overwritten or conflated High Validate and commit Spec 012 first; never reset/stash; inspect every staged path before each commit.
Production deploy does not match repository head High Record full SHA before build/deploy; push first; follow exact CI; verify deployment metadata and cache-busted live assets.
Public PointSite is accidentally published Critical Operate only in PointCommunity/pointsite-builder; keep PRODUCTION_ENABLED=false; do not invoke content publish.

Rollback

If live verification fails, leave the last known-good deployment available, create a reviewable revert commit for the bad Builder release, push it to main, deploy the revert through the same command, and re-run health/authenticated browser verification. Do not rewrite shared history or mutate draft revisions in place.
