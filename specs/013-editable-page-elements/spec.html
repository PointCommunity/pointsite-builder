PointSite Builder · Spec 013

Editable Page Heroes

Convert the remaining hard-coded non-home page hero into the existing Builder Hero element so authors can select, edit, move, duplicate, remove, overlap, and replace it like every other page-specific element.

Draft · awaiting human approval

Assumptions for review

  1. “All elements” applies to page-specific content. The persistent global footer keeps its established centralized settings process and remains outside each page's element tree.
  2. Structural accessibility/runtime nodes—the skip link, main landmark, and editor selection wrappers—are not author content and remain code-owned.
  3. The existing Hero option must be reused; only a page-hero style is added. No duplicate Hero or Footer option is created.
  4. Existing visual content is preserved by deterministic migration. Historical revisions remain immutable and readable.
  5. The pending Spec 012 changes are verified and committed separately, then both commits ship in one exact Builder production release.

Objective

Give PointSite maintainers one consistent page-authoring model: anything that specifically belongs to a page is represented by a registered element inside that page's structure. Success means no non-home hero is injected around the editable tree, while the global footer remains centralized.

Functional requirements

  • FR-001: Every legacy non-home hero becomes an existing Hero element without losing eyebrow, heading, introduction, image, or presentation.
  • FR-002: Hero exposes a Point page-hero layout style inside the existing Hero inspector; no second hero catalog entry is created.
  • FR-003: The migrated Hero participates in Page structure and standard select, move, duplicate, remove, drag, replace, and section-position behavior.
  • FR-004: Page details retains page identity, route, status/layout, browser metadata, and sharing metadata, but removes visual hero fields.
  • FR-005: A new standard page starts with a registered Hero rather than hidden frame chrome.
  • FR-006: Schema version 7 drafts migrate once and deterministically to version 8; versions 0–7 still load through the migration chain.
  • FR-007: Removing or reordering the Hero persists through save and reload.
  • FR-008: The global footer keeps its centralized settings and persistent cross-page rendering.
  • FR-009: Public PointSite production publishing remains disabled and untouched.

Tech stack

Code style

export function createEditablePageHeroSection(page: LegacyPageChrome): SectionBlock {
  return createCompatibilitySection({
    id: derivedUuid(page.id, PAGE_HERO_MASK),
    type: 'hero',
    variant: 'pageHero',
    heading: page.title,
    actions: [],
    // legacy author content is copied without semantic reinterpretation
  });
}

Use explicit discriminated unions, deterministic IDs, pure migration helpers, strict schemas, and state-based tests. Do not create a second data path for the same visual surface.

Testing strategy

  • RED first: version-7 migration, renderer ownership, new-page defaults, and browser authoring tests must fail against the current implementation.
  • Unit: exact migrated values, IDs, idempotence, schema rejection, catalog uniqueness, renderer semantics, footer continuity, and media usage.
  • Browser: the non-home Hero appears in Page structure and can be selected, edited, moved, duplicated, removed, replaced, saved, and observed after reload; the centralized footer remains present.
  • Regression: all 11 routes retain expected copy/media; accessibility and responsive checks remain green.
  • Release: exact pushed head passes GitHub Quality, deploys once to Builder production, and passes authenticated browser plus /api/health verification.

Boundaries

Always: preserve pending Spec 012 work; keep migration deterministic; preserve the centralized footer process; verify every supported browser; deploy only exact committed/pushed Builder head.

Ask first: changing the centralized footer content model; adding a duplicate Hero option; changing public PointSite publishing; deleting historical revisions.

Never: expose credentials; write to public PointSite; mutate historical revisions in place; silently drop page hero content; move the footer into page-specific content; claim live success from local tests.

Success criteria

  • Every page-specific visual surface across all 11 default pages is represented in Page structure, while the global footer remains centralized.
  • The reported non-home hero is no longer rendered outside the editable tree.
  • Hero is reused, no Footer is registered, and the catalog contains no duplicate element purpose.
  • The one active version-7 draft upgrades losslessly to version 8 on read and saves as version 8.
  • Full local and CI gates pass; exact head is deployed and verified at builder.pointatx.org.
  • The public PointSite repository and deployment are unchanged.
