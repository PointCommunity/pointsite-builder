Spec 013 · analysis

Editable Page Heroes

Repository, live-browser, schema, renderer, editor, migration, and release analysis for moving the remaining page-specific visual chrome into the Builder's element tree.

Confirmed root cause

On every non-home page, SiteFrame renders a .page-hero directly from page-level title, eyebrow, intro, and heroMediaId fields before the Puck-owned children. It therefore never appears in Page structure, cannot be selected as a block, and cannot participate in move, duplicate, remove, replace, or overlap controls.

The live Builder reproduced this on “Who We Are”: the hero was present in the iframe but absent from the Page structure list. The list began with Site header, then Cards and Rich text sections.

Static-surface audit

Visible surface Current ownership Finding Decision
Site header Editable section containing Image and Navigation elements Already in the page tree after Spec 011 Keep
Home hero Existing Hero element Selectable, movable, duplicable, removable, and replaceable Keep
Non-home hero Hard-coded SiteFrame chrome Reported defect Migrate into the existing Hero element with a page-hero layout style
Page content Section and element tree Already editable Keep
Global footer Hard-coded SiteFrame chrome with a settings shortcut Persistent shared site chrome with an established centralized editor Keep centralized and outside the page-level element contract
Skip link and main landmark Accessibility/runtime structure Not author content Remain code-owned

Catalog decision

A Hero element already exists, so creating a second hero option would duplicate the catalog. The existing Hero receives a pageHero layout style that preserves the current non-home presentation while exposing the same content, media, surface, alignment, and action controls as other heroes.

The Footer remains persistent across pages and continues to use its established centralized settings. It is not a page-specific element and no Footer catalog option will be added.

Persistence and migration evidence

  • The current schema and renderer identity is version 7 / 7.0.0.
  • The remote database has one active draft whose latest revision is version 7.
  • Historical revisions exist at versions 1, 2, 3, 5, 6, and 7 and must remain readable.
  • The repository already migrates documents deterministically when they are read or saved.
  • Spec 013 therefore requires a deterministic 7-to-8 migration, not an ad hoc UI transform.
