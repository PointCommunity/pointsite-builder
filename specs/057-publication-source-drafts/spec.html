PointSite Builder · Issue #57 · governing feature specification

Reusable drafts from published Staging or Production

Editors choose a named, currently verified publication and create an independent copy. Drafts keep immutable history. A compact Production-baseline status describes source lineage, not whether later edits are live.

Requirements

  1. FR-057-01: Creation requires an explicit Staging or Production choice in the workspace. Cancel creates nothing. A source unavailable, changed, unverified, incompatible, or missing required media fails without another source or template fallback.
  2. FR-057-02: Capture one verified deployment, release marker, immutable source document, manifest, output inventory and referenced public media. Check identity again after capture. Copy referenced assets into draft-owned storage; never link a private draft to mutable public paths.
  3. FR-057-03: At least four independent drafts survive edit, publication replacement, reload and later reuse. Reuse never merges current Production. Duplicate and existing drafts without proven lineage show unknown baseline.
  4. FR-057-04: Show Published - Revision N when the draft's proven Production baseline remains current, Behind Production - Revision N after replacement, and an explicit unknown-baseline line otherwise. Staging source is named separately; Staging-only content must never appear to be live Production.
  5. FR-057-05: Initial displayed count is 0. Every acknowledged content-changing save advances it by one. No-op saves, labeling and rename do not. Staging publication does not reset it.
  6. FR-057-06: Only a durably verified Production publication advances the publishing draft's baseline and resets the count at its exact captured revision. Saves made after capture remain counted. Failed, cancelled, queued, accepted, or unverified attempts never reset it.
  7. FR-057-07: Production replacement makes previous proven baselines Behind without modifying drafts or their history. Production rollback is a new verified release identity; it does not retroactively reset unrelated drafts.
  8. FR-057-08: Baseline evidence persists server-side. Concurrent saves retain compare-and-swap and checkout guards; publication status never authorizes a mutation. Migration leaves uncertain existing drafts unknown and retains immutable provenance.
  9. FR-057-09: Same revision typography/location as existing editor header. Explain baseline, unpublished edits, and Staging lineage accessibly. Status remains clear by words on narrow and wide layouts, without color dependence.

Status rules

Count: latest immutable sequence minus captured baseline sequence; creation starts at sequence 1. A verified Production publication sets the baseline sequence to the captured revision's sequence, never the latest sequence.

Published: verified baseline release identity equals current Production release identity. Behind: a proven baseline exists but a different verified Production release is current. Unknown: no verified baseline link, or current release identity cannot be confirmed.

Staging lineage: a verified Staging candidate can inherit a Production baseline only through the matching locally recorded candidate, origin, revision, and saved lineage. Otherwise it stays unknown. The status describes baseline; the Staging document is not claimed live.

Acceptance and verification

Exercise both source choices, changed/unavailable publication, asset checks, four seasonal drafts, saved edits, Staging replacement, verified Production replacement, older-draft republication, post-capture edits, failed attempts, migration and reload. Verify server roles, checkout, idempotency, keyboard/focus, screen reader text, and responsive header. Run repository QA sequentially: npm run check, npm run test:performance, then npm run test:e2e.

Boundaries

Do not bypass public Production publication authority or mutate PointSite to manufacture status. No scheduling, automatic merging, destructive history reset, extra Builder environment, dependency addition, or transfer of Canary draft data to Production. Application Canary and Production deployment follow Builder pipeline policy.
