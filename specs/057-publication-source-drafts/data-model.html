Lineage, not renumbered history

Migration 0037_draft_publication_baselines.sql adds a narrow per-draft status projection. The immutable revisions.sequence and draft_production_sources.provenance_json remain unchanged.

Field Meaning
source_target Captured Staging, Production, or unproven origin. It never confers publication rights.
baseline_release_id Verified public Production release identity. Null means unknown; historical IDs survive metadata retention without a destructive foreign-key cascade.
baseline_sequence The exact captured immutable revision sequence whose publication reset the display count. Initial import uses 1.

Source and status transitions

Source preview pins public commit, deployment, artifact digest and optional candidate checksum. Creation recaptures and compares that identity before any DB write. Independent draft-owned images and immutable provenance commit with the initial revision. Production import links only to the exact latest local release with matching commit, artifact and deployment. Staging import links only to an exact verified Production candidate/artifact record; otherwise its Production baseline stays unknown.

A content-changing save advances immutable sequence; display count is max(0, latest sequence - baseline sequence). Verified Production release insertion runs the additive trigger for the pinned publication_inputs.revision_id. The publishing draft gets the new release ID and captured sequence. Every other draft keeps its baseline row; comparing it with the latest release produces Behind. Failed jobs and Staging publication never insert a Production release and cannot reset counts.

Upgrade and rollback

Upgrade test applies migrations 1–36, seeds old drafts/source provenance, then applies 37. Only an exact current release match backfills Published; unproven old drafts remain Unknown. Native SQLite integrity and foreign-key checks run before startup. Migration is additive; previous application image ignores the new table and its old revision/history paths stay readable. A rollback restores the recorded previous application digest via GitOps, not database rows. Do not delete baseline/source rows or restore a database without scoped PM approval.

Verification limit

Server status compares durable Builder-controlled release records. An out-of-band public-site deployment not recorded in Builder can invalidate that projection; source capture fails closed when its deployment/marker is unconfirmed. Operational reconciliation must detect external drift before claiming that a new application candidate is fully verified live. No public content is published merely to test these status rules.
