PointSite Builder · Issue #57 · implementation plan

Verified source first, baseline status second

Research readback

Current D1 creation already imports verified Production and owns copied images through server/production-source.ts, D1DraftRepository.createDraft, and migration 0036. The UI still offers no source choice. The Production baseline is a captured legacy deployment in migration 0029; verified Builder Production jobs append durable releases in verifiedReleaseStatement. Staging and Staging Canary currently expose format-2 live release markers plus content manifests. Staging selection must use the runtime's fixed destination, never a browser-selected repository URL.

Decisions

  1. Extend existing bounded immutable-public-source capture to fixed Staging destinations. Retain legacy Production baseline handling. Server accepts source enum and never falls back to default content in configured native deployments.
  2. Add an additive draft-baseline record. Match captured Production provenance to the current verified release; inherit Staging lineage only with exact local candidate/identity evidence. Existing uncertain drafts remain unknown. Never infer lineage from visual content similarity.
  3. Compute displayed count from immutable revision sequence minus baseline sequence. A verified-release insertion alone changes a publishing draft's baseline using its pinned exact publication input. Other drafts become Behind by comparing release IDs, without updates to their histories.
  4. Return server-calculated status in draft list and detail. Client renders compact status in the current editor line and concise explanation. Keep source identity visible in create flow.

Risks and recovery

Staging provenance might not link to a local candidate, especially after metadata retention or across Canary/Production; show unknown. A public release outside the Builder can make local release records stale; fail closed on uncertain current identity. Additive migration and old image compatibility: old code ignores the new table. Never delete immutable revisions or existing production-source rows. Revert application image through GitOps if needed; data restoration requires separate approval.

Sequence and checkpoints

Tasks in ordered task list move from source capture and safe creation, to persisted baseline/counter, to verified publishing reset, to accessible UI/browser checks. Every logic slice starts with a failing test and ends with focused checks. Full QA runs sequentially before PR review, exact-head Quality, and Canary.
