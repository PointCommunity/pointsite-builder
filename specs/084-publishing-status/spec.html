Issue 84: Accurate publication status

Specification, research, implementation plan and tasks. Scope follows Issue 84. Baseline: 0d743077a3d459ce5f94886a7c49a3e56b0d4d57.

Evidence and source of truth

  • dispatch.ts sends repository_dispatch, receives no run identity, and retries at most six times with durable backoff. runner.ts reserves signed run identity before build, commit and deployment authority. recovery.ts and retry.ts enforce slots, roles, identity, idempotency and captured bases.
  • jobs.ts currently reads provider jobs only after reservation. progress.ts cannot see run-level zero-job failures. PublicationProgress.tsx animates queued jobs. Both publishing views hide manual refresh during normal polling and discard the previous snapshot on read failure.
  • The live caller workflows use exact run titles “Publish Staging candidate <job UUID>” and “Publish accepted public candidate <job UUID>”. GitHub's workflow run API exposes run status, conclusion, display_title, event, repository, SHA, path and attempt independently from jobs.
  • Durable Builder job state and signed milestones own completion and authority. Diagnostic provider observations never authorize acceptance, deployment, success or slot release. Cancellation separately fences authority and freshly verifies matching terminal native runs before releasing its slot. A correlated stopped provider run overrides apparent progress and offers guarded recovery.

Behavior contract

  1. Read exact recorded run attempts, including run-level outcomes with zero jobs. Before reservation, search one bounded page of repository_dispatch runs at the captured SHA; require exact job UUID title, repository identity, caller path, main branch, event and request time. Ambiguous or missing matches mean unconfirmed, never guessed execution.
  2. Show queued, running/building, preparing, deploying, verifying, completed, stopped/cancelled and unavailable status distinctly. Without confirmation, say “Start not confirmed”; after two minutes request attention. Never animate unconfirmed, stale, terminal or unavailable status. Use a static milestone bar and visual steps without invented time percentages.
  3. Show last successful Builder check and provider check separately, including provider backoff. Cache/coalesce provider reads for at least sixty seconds and honor rate limits. Poll at ten-second intervals with one read in flight; stop automatic monitoring after a read failure or fifteen minutes of continuous monitoring. Manual check remains available and starts a new bounded monitoring window.
  4. Retain the last snapshot on read failure; disable mutations until fresh authority can be read. Ignore reads belonging to a previous draft or unmounted view. Reopening reads durable state. Keep cancellation and supported recovery in the main action area. Explain unavailable retry, stale base, expired authority and post-deployment blockers.
  5. Reuse existing cancel, reconcile, retry and verify endpoints. Cancellation before deployment authorization invalidates late runner callbacks atomically. Retry never changes captured inputs or bypasses current base/caller/role/slot checks. Provider observations never become runner reservation credentials.
  6. Staging and Production share presentation and diagnostic rules while retaining fixed independent lane identities. Status actions are keyboard/touch accessible; action completion focuses the heading; polite announcements report meaningful state. Reduced motion shows static status.
