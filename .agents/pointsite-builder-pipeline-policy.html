PointSite Builder Development Pipeline

This is the shared policy source for repository-owned PointSite Builder workflow skills. It governs development and deployment of the private Builder application, not publication of the public PointSite.

Objective and authority

The agent carries one PM-selected GitHub Issue from an approved draft through specification, implementation, review, exact-revision deployment, live verification, and closure. The PM is GitHub user brimdor. Repository instructions and live GitHub/Cloudflare state take precedence over stale assumptions.

Issue model

Every open Issue belongs to the Project with Status, Priority, Impact, and Effort populated. Backlog cards are open and unassigned. Active means Status In Progress or In Review; exactly one Issue maximum may be active and it is assigned only to brimdor. On Hold is inactive and requires an explicit PM pause. Dependabot pull requests are maintenance automation and do not consume the active slot.

State flow

  1. The agent researches and shows the complete HTML Issue plus metadata. Only Approved to create this exact GitHub Issue authorizes creation of that draft.
  2. The Issue is created open and unassigned, added to the Project, fully classified, and set to Backlog. When the PM selects it, the agent moves it to In Progress, assigns only brimdor, and verifies it is the sole active Issue.
  3. The agent works from current origin/main on issue/<number>-<slug>, maintaining appropriate spec, plan, task, test, migration, security, accessibility, and operations evidence.
  4. The agent creates a PR with Refs #<number>, completes full review and local browser QA, remediates every finding, requires every GitHub Quality job to pass for the exact head, and moves the verified card to In Review.
  5. Unless the PM requested an earlier stop, the agent squash-merges the verified PR, proves the merge tree equals the reviewed tree, and waits for GitHub Quality on the exact origin/main commit.
  6. The agent records the current Cloudflare version, applies rehearsed backward-compatible D1 migrations when required, runs npm run deploy from the clean exact main revision, and verifies the new Worker version receives 100% traffic.
  7. The agent verifies /api/health, cache-busted HTML and derived assets, and relevant live behavior. Only then does it record evidence, move the card to Done, verify the resulting Issue closure, unassign it, and confirm the active slot is empty.

Agent-owned Project movement

The PM never has to drag a card, select a Status, or repair Project metadata. Human Issue approval, work selection, pause or resume requests, findings, and requested stopping points are decision gates; the agent performs and immediately verifies the corresponding Project transition.

Candidate identity

A reviewed candidate is the tuple of Issue, PR URL, exact PR head commit and tree, test evidence, and GitHub Quality run. A released candidate adds the main merge commit and tree, exact-main Quality run, previous and new Cloudflare version IDs, migration evidence, deployment result, and live-verification result. The merge tree must equal the reviewed tree.

Lean completion evidence

Routine Issue completion uses the existing Issue or PR for concise durable release evidence and a concise final chat handoff for the PM. Do not create or open a standalone acceptance report, duplicate closeout document, or summary artifact unless the PM explicitly requests that artifact as a deliverable. Specifications, tests, CI, deployment output, and live verification are the authoritative evidence; do not duplicate them into another document.

Direct production and recovery

Builder application work goes directly to its sole production environment after agent QA and exact-main CI. There is no routine second approval and no staging or Canary promotion. Before deployment, record the current 100% Cloudflare version. On runtime failure, roll back to that version and verify recovery. Keep the Issue open and assigned, then make the durable source fix through a reviewable revert or same-Issue remediation. Destructive schema or data recovery always requires PM authorization.

GitHub enforcement limitation

GitHub currently rejects branch protection and repository rulesets for this private repository at the organization plan level. Repository skills and deterministic audits enforce the PR, exact-tree, and Quality contract and report this limitation. They never claim unavailable branch rules are active.

Boundaries

  • Always preserve unrelated user-owned work and use only task-owned commits.
  • Always keep migrations backward compatible with the recorded rollback version.
  • Always verify the exact remote main commit and GitHub Quality before deployment.
  • Never request credentials, expose secrets, or weaken authentication for evidence.
  • Never deploy or publish the public PointSite from this pipeline.
  • Never close an Issue after merge alone; verified production is completion.
  • Never generate or open a redundant closeout report for routine Issue completion.
