Pipeliner maintenance and local QA

Adoption and framework updates require no PM Testing, PM acceptance or bootstrap-completion approval. The agent completes test suites and agent testing, remediates findings, verifies publication and cleanup, and reports completion. Application PM gates remain mandatory for product work.

Pipeliner adoption, alignment, updates, and explicitly requested monitor management are direct framework maintenance. They require no GitHub Issue, active-slot transition, or Issue approval. Verify and publish a focused maintenance PR, then report the installed revision. Maintenance never deploys Builder or schedules a monitor by default.

The product lifecycle below remains authoritative for application Issues. Full application, browser and performance QA runs locally on the configured Mac; GitHub Quality runs lightweight pipeline and security checks only. Its success never substitutes for complete local evidence. Product releases require exact Canary approval before Production promotion; final product acceptance remains the Production Showcase.

PointSite Builder Development Pipeline

This is the shared policy source for repository-owned PointSite Builder workflow skills. It governs development and deployment of the private Builder application, not publication of the public PointSite.

Objective and authority

The agent carries one PM-selected GitHub Issue from an approved draft through specification, implementation, review, exact-revision deployment, live verification, and closure. The PM is GitHub user brimdor. Repository instructions and live GitHub/Gitea/Argo state take precedence over stale assumptions.

Issue model

Every open Issue belongs to the Project with Status, Priority, Impact, and Effort populated. Backlog cards are open and unassigned. Active means Status In Progress or In Review; exactly one Issue maximum may be active and it is assigned only to brimdor. On Hold is inactive and requires an explicit PM pause. Dependabot pull requests are maintenance automation and do not consume the active slot.

State flow

  1. The agent researches and shows the complete HTML Issue plus metadata. Only Approved to create this exact GitHub Issue authorizes creation of that draft.
  2. The Issue is created open and unassigned, added to the Project, fully classified, and set to Backlog. When the PM selects it, the agent moves it to In Progress, assigns only brimdor, and verifies it is the sole active Issue.
  3. The agent works from current origin/main on issue/<number>-<slug>, maintaining appropriate spec, plan, task, test, migration, security, accessibility, and operations evidence.
  4. The agent creates a PR with Refs #<number>, completes full review and local browser QA, remediates every finding, requires every GitHub Quality job to pass for the exact head, and moves the verified card to In Review.
  5. The agent builds clean pushed source locally for linux/amd64, publishes an immutable image to Zot and deploys Canary through Gitea homelab GitOps. Record source/tree, image digest and Canary configuration commit; verify health and authenticated behavior, then present PM tests.
  6. Explicit PM approval of the exact healthy Canary candidate is required before merge and Production promotion. Prove the merge tree equals the reviewed image source tree, wait for exact-main Quality, record the previous Production image/configuration and promote the same approved digest without rebuilding. Verify Argo reconciliation and independent Production data.
  7. The agent verifies /api/health, cache-busted HTML and derived assets, and relevant live behavior, records release evidence, and presents a linked production Showcase with numbered, change-specific PM testing steps. The Issue remains open, assigned, and In Review.
  8. The PM tests the production Showcase. Findings return the Issue to In Progress and require a new remediation, QA, merge, deployment, and Showcase cycle. Only Approved to complete Issue #<number> for the unchanged released candidate authorizes the agent to move the card to Done, verify closure, unassign it, and confirm the active slot is empty.

Agent-owned Project movement

The PM never has to drag a card, select a Status, or repair Project metadata. Human Issue approval, work selection, pause or resume requests, findings, and requested stopping points are decision gates; the agent performs and immediately verifies the corresponding Project transition.

Candidate identity

A reviewed candidate is the tuple of Issue, PR URL, exact PR head commit and tree, test evidence, and GitHub Quality run. A released candidate adds the main merge commit and tree, exact-main Quality run, previous and new image digests, GitOps revision, migration evidence, deployment result, and live-verification result. The merge tree must equal the reviewed tree. PM completion approval applies only to this full released tuple and is invalid after any source, tree, dependency, migration, image, deployment configuration, or behavior change.

Production Showcase and PM acceptance

Canary at https://builder-canary.eaglepass.io is the pre-promotion PM testing target. Production at https://builder.eaglepass.io is the final Builder Showcase. After agent QA, exact-head and exact-main Quality, deployment, and live verification, the agent presents that hyperlink with prerequisites, numbered actions, expected results, and focused regression checks derived from the actual change. Agent QA and production health do not substitute for PM review and testing. The Issue remains In Review until the PM states Approved to complete Issue #<number> for the current candidate.

Exact Canary approval permits Production promotion; separate Production Showcase approval permits Issue completion.

Lean completion evidence

Routine Issue completion uses the existing Issue or PR for concise durable release evidence and a concise final chat handoff for the PM. Do not create or open a standalone acceptance report, duplicate closeout document, or summary artifact unless the PM explicitly requests that artifact as a deliverable. Specifications, tests, CI, deployment output, and live verification are the authoritative evidence; do not duplicate them into another document.

Immutable promotion and recovery

Builder application work goes to Canary after agent QA and exact-head CI. Production requires explicit approval of the exact source/tree, image digest and Canary GitOps configuration. Promote the same digest without rebuilding. Preserve independent Production host, secrets, sessions and persistent storage; never promote Canary drafts or approvals. Before deployment, record and retain the previous Production image/configuration. On runtime failure, roll back through GitOps and verify recovery. Keep the Issue open and assigned, then make the durable source fix through a reviewable revert or same-Issue remediation. Destructive schema or data recovery always requires PM authorization.

GitHub enforcement limitation

The source repository is public; its Project remains private. Branch protection and rulesets are intentionally disabled, matching the adopted profile and current settings. Repository skills enforce PR review, complete local QA, exact-tree identity and lightweight Quality checks. Inspect live settings before reporting them; enabling protection requires explicit PM direction.

Boundaries

  • Always keep migrations backward compatible with the recorded rollback version.
  • Always verify exact pushed source and GitHub Quality before Canary; verify reviewed-tree equality and exact-main Quality before Production.
