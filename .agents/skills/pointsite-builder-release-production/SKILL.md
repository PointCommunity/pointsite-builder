# Release PointSite Builder Production

Pipeliner adoption, alignment, updates and requested monitor management use the direct framework-maintenance exception in `AGENTS.md`, without a GitHub Issue or active-slot transition. For product Issues, lead status and approval messages with the owning Issue and retain this specialized Builder workflow. Application QA runs locally; GitHub Quality provides lightweight contract and security evidence only.

Read `AGENTS.md`, `.agents/pointsite-builder-pipeline-policy.html`, the active Issue, merged PR, exact Canary approval and candidate evidence, current Git and CI state, and the migration/backup plan. Run only from `pointsite-builder-close-issue` unless the PM explicitly requests a standalone Builder deployment; standalone requests still require exact-candidate approval. Use `npm run release:inspect` before PM approval and `npm run release:production` only after approval. The legacy `scripts/release-native.mjs production` action fails closed.

1. Require clean local `main` with `HEAD == origin/main`, successful GitHub Quality for that exact commit, and a merge tree equal to the approved Canary source tree. Verify the PM approved the unchanged healthy Canary source/tree, image digest, configuration commit and inspected Linode baseline. A changed tree, Canary configuration or Linode baseline requires fresh review and approval.
2. Confirm the current production route in Gitea `ops/homelab` `system/cloudflared/values.yaml`: the explicit `builder.eaglepass.io` rule targets the `pointsite-builder` Linode (handoff IP `45.33.2.134`) before the wildcard rule; `builder-canary.eaglepass.io` still uses homelab ingress. Verify the Linode firewall restricts TCP/3000 to the tunnel egress; never expose it publicly or repurpose Canary. Use only an already-authorized SSH key; never request or print credentials.
3. Keep the canonical homelab GitOps checkout clean and fast-forwarded to Gitea `master`. The Linode `/opt/pointsite-builder/app` must be a full Git checkout with its own `.git` directory so the isolated build container can verify source identity. From clean pushed Canary source, run `npm run release:inspect -- --candidate artifacts/native-candidate.json`. It checks Quality, the exact healthy Canary digest and GitOps revision, the Cloudflare route in current homelab GitOps, and the live Linode wrapper and service hashes over strict SSH. The resulting `productionConfigHash` binds the approval to this Linode baseline. A changed baseline requires a fresh inspection and exact PM approval. Do not print or replace `/etc/pointsite-builder/environment`, the GitHub App key, or runtime secrets.
4. Before deployment, verify the PM approved the exact inspected tuple. For SQLite migrations, require native fresh/upgrade tests, backward compatibility and a deletion-safe restore rehearsal; destructive data/schema restoration needs scoped PM approval. The deploy command requires a clean, pushed merged `main` with the reviewed Canary tree and passing exact-main Quality.
5. Run `npm run release:production -- --candidate artifacts/native-candidate.json --approval /absolute/path/to/approval.json`. It rechecks the Linode baseline, verifies the current service and separate encrypted backup mount, creates a fresh native recovery point under `/opt/pointsite-builder/backups/native/`, and stops if any preflight fails. It checks out the exact merged `main` commit, runs `npm ci` and `npm run build:native` inside a pinned linux/amd64 Node build container, verifies `dist/release.json` matches the approved source/tree, then packages the runtime image with revision and tree labels. The runtime `Containerfile` only copies `dist`; never package stale files from an earlier checkout. It saves the runtime wrapper, changes only the pinned `localhost/pointsite-builder:<COMMIT>` tag, restarts `pointsite-builder.service`, and verifies the new image ID. The Linode build may have a different digest from Canary; record the actual Production image ID and never claim same-digest promotion.
6. The command checks local `/healthz` and `/readyz` with the Production Host header, mounts, a second fresh native backup, public Production source/tree health, the homelab Canary route, and cache-busted HTML/assets on both origins. It restores the previous pinned image if a post-switch gate fails. Review `journalctl -u pointsite-builder.service --no-pager -n 80` for migration, mount and permission errors without printing secrets. Smoke-test authenticated existing workspace data with a non-destructive action when supported access exists; report the gap if it does not.
7. Add concise Issue or PR evidence: approved Canary identity, merge commit/tree, exact-main Quality, previous/new Linode image tags and IDs, backup and mount checks, service/local/external health, both route checks, and authenticated behavior or its limitation. Return the released identity and Production URL to `pointsite-builder-review-issue` for its Showcase. The Showcase needs no second approval. If the approved Issue is fully accepted, close it without another approval; otherwise keep it open, assigned and active. Do not duplicate this evidence into a standalone report unless requested.

On failure, restore the saved wrapper's previous image reference, restart `pointsite-builder.service`, and verify local health, state, backup capability, and both public routes. Keep the Cloudflare route pointed at Linode for normal image rollback; consider the retained homelab deployment only if the Linode cannot be made healthy. Preserve new and previous images, data, recovery state, and backup artifacts for diagnosis. Keep the Issue open and use a reviewable revert or same-Issue remediation. After verified success, remove only task-created test artifacts and unreferenced images; retain active and rollback images.

This skill never deploys or publishes the public PointSite and never writes to `PointCommunity/pointsite` or `PointCommunity/pointsite-staging`.
